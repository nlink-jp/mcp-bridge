# ADR-0007: トークンの更新はプロセス間で 1 本ずつ行い、そのたびに保存先を読み直す

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-11-26 |
| Binds | mcp-bridge |
| Decision makers | nlink-jp maintainers |
| Triggered by | 利用者からの改善提案（2026-11-26）。Atlassian Remote MCP で、しばらく使わずに置いたあとの更新が `invalid_grant` で失敗し、`mcp-bridge login` をやり直すしかなくなる現象が繰り返し起きていた |

## Context

MCP クライアントはサーバを stdio の子プロセスとして、セッションや画面ごとに起動する。
このため、同じサーバに対する `mcp-bridge run` が何本も同時に動くのが普通の状態である。
報告者の環境では 1 サーバあたり 6 本（Claude Desktop 2 本、Claude Code 2 本、gem-agent 2 本）、
保守者の手元でも github・nanokvm・obsidian がそれぞれ 6 本ずつ動いていた（2026-11-26、`ps` で確認）。
これらは 1 つの `state/<server>/tokens.json` を共有している。

v0.3.0 の `oauth.Provider` は、起動時に `tokens.json` を 1 回だけ読み、その後は refresh token を
メモリ上に持ち続ける。更新の直前にファイルを読み直さず、排他は `sync.Mutex`（プロセスの中だけ）である。

使うたびに refresh token を新しいものに置き換え、古いものを使えなくするサーバ（OAuth 2.1 と
RFC 9700 が公開クライアントに勧める挙動）では、これが次のように壊れる。

1. プロセス A と B が同じ `RT0` を読んで起動する。
2. A が `RT0` で更新し、`RT1` を受け取って保存する。`RT0` は使用済みになる。
3. B がメモリ上の `RT0` で更新し、`invalid_grant` で失敗する。
4. 使用済みの refresh token が再び提示されたら grant ごと無効にするサーバ（reuse detection）では、
   `RT1` も無効になる。ファイルに残ったログインは死に、あとから起動したプロセスも動かない。

しばらく放置したあとに起きやすいのは、どのプロセスも同じファイルから同じ `expires_at` を読むためである。
全プロセスのアクセストークンがほぼ同時に期限切れになり、次の操作で各プロセスが数秒のうちに一斉に更新しに行く。

提案書の再現テスト（2 つの `Provider` が 1 つのファイルを共有し、使い捨ての refresh token を発行する
テスト用サーバに対して更新する）は、v0.3.0 で報告と同じエラー文を出して失敗した。同じく 6 本が同時に動く
Entra ID（m365 系 5 サーバ）では失敗が 1 件も記録されていない。Microsoft の文書によれば、Entra ID は
使用済みの refresh token を無効にしない。観測と整合する。Atlassian が reuse detection を持つかどうかを
示す公開文書は見つかっていない。ただし、使い捨ての refresh token を発行するサーバであれば、
reuse detection が無くても手順 3 で B は失敗する。この欠陥は Atlassian の仕様とは関係なく存在する。

調べる中で、同じ原因から来る欠陥がほかに 2 つ見つかった。

- **ログインし直しても、動いている bridge は直らない。** `invalid_grant` で失敗したプロセスは使用済みの
  refresh token を持ち続け、次の更新でも同じものを送る。利用者が `mcp-bridge login` をやり直しても、
  そのプロセスはファイルを読まないので、MCP クライアントを再起動するまで失敗し続ける。
- **ログアウトしても、動いている bridge がログインを書き戻す。** `logout` は `tokens.json` を消すが、
  動いているプロセスは次の更新でメモリ上の refresh token を使い、結果をファイルに保存する。
  消したはずのログインが元に戻る。

## Decision

**保存先（`tokens.json`）を、そのサーバのログインの唯一の正本とする。** プロセスのメモリ上の値は
その写しであり、更新するときや諦める前には、必ず正本を読み直してから判断する。

### 1. 書き換えはプロセス間で 1 本ずつ行う

`tokens.json` を読んで判断し書き換える処理は、同じディレクトリの `tokens.json.lock`（モード 0600）に
OS の排他ロックを掛けて行う。Unix では `flock(LOCK_EX)`、Windows では `LockFileEx` を、標準ライブラリの
`syscall` から呼ぶ。外部依存は増えない。

- ロックは `tokens.json` そのものではなく別のファイルに掛ける。`SaveTokens` は一時ファイルを
  rename して置き換えるので、`tokens.json` に掛けたロックは置き換えのたびに別のファイルの上に残ってしまう。
- ロックを持ったプロセスが落ちると、カーネルがロックを解放する。古いロックが残る問題は起きない。
- `tokens.json.lock` は消さない。ほかのプロセスが掴んでいるかもしれないロックファイルを消すと、
  2 つのプロセスが別々のファイルにロックを掛けることになり、排他が成り立たなくなる。
- ロックの中で行うのは、ファイルの読み直し・判断・更新の通信・保存だけである。更新の通信には
  既存の 30 秒の上限がある。

### 2. 更新が要るときは、ロックの中で読み直して判断する

`Token()` が「メモリ上のトークンでは足りない」と判断したとき（refresh token があってアクセストークンが
期限切れ、またはサーバに拒否された）、ロックを取ってファイルを読み直し、次の順で決める。

| ファイルの状態 | すること |
|---------------|---------|
| ファイルが無い | ログアウトされたとみなす。更新せず、`mcp-bridge login` を案内するエラーを返す |
| 読めない・壊れている | 更新せず、読めなかった理由と `mcp-bridge login` を案内するエラーを返す |
| アクセストークンが使える（空でない・このプロセスがサーバに拒否されたものでない・期限内か、refresh token が無く期限を判断しない） | 更新せずに採用する（別のプロセスの更新か、新しいログインの結果） |
| 上のどれでもなく、refresh token がある | ファイル上の refresh token で更新し、結果を保存する |
| 上のどれでもなく、refresh token が無い | 更新できない。サーバに拒否されたことと `mcp-bridge login` を案内するエラーを返す |

「このプロセスがサーバに拒否されたもの」は、401 を受けた時点のアクセストークンを覚えておいて判断する。
ファイルにまだ同じトークンが残っていても、それは採用しない。

例外が 1 つある。このプロセスが更新した結果を保存できなかった（読み取り専用のディレクトリ、空き容量の不足）
あと、ファイルがその時のまま変わっていなければ、新しいのはメモリの方である。この場合はファイルではなく
メモリ上の refresh token で更新する。ファイルの方を使うと、使い捨ての refresh token を発行するサーバでは、
1 本しか動いていなくても使用済みのトークンを送ることになる（v0.3.0 はメモリ上の値を使うので起きなかった）。

refresh token が無く拒否もされていないトークンは、これまでどおりロックもファイルの読み直しもせずに
そのまま返す（ADR-0003）。起動時の最初の読み込みもロックの中で行う。

### 3. `login` と `logout` も同じロックの中で書き換える

`login` はブラウザでの操作を待つ間はロックを取らず、得たトークンを保存するところだけをロックの中で行う。
`logout` はファイルを消すところをロックの中で行う。これで、更新の途中にログインやログアウトが割り込んで、
古いログインの更新結果が新しいログインを上書きすることも、消したログインが書き戻されることも起きない。

### 4. ロックが使えないときと、待ちきれないときは分けて扱う

**ロックファイルを開けない**（読み取り専用の state ディレクトリ、ファイルロックの無い OS）場合は、
そのことを stderr に 1 行出したうえで、ロックなしで手順 2 を行う。どのプロセスもロックを使えない環境なので、
待っても調整は成り立たない。ロックのせいで動くはずの更新を失敗させることはしない（既存の
`TestUnwritableTokenFileWarnsButSucceeds` が求める性質）。

**ほかのプロセスがロックを持ったまま、一定時間（45 秒）待っても取れない**場合は、その要求を
エラーにする（「ほかの mcp-bridge がこのサーバのトークンを更新中なので、もう一度試す」）。
refresh token は送らない。待ちは前の保持者の分だけ積み重なる（1 本目の更新が 30 秒の上限で失敗し、
2 本目が同じ refresh token で更新を始めた間に、3 本目が上限に達する）ので、上限のあとでロックなしに
更新すると、この ADR が防ぎたい「同じ refresh token の同時提示」が応答の遅いサーバで起きる。
要求を 1 回失敗させる方が、保存済みのログインを失うよりも軽い。MCP クライアントには JSON-RPC の
エラーとして応答が返る（ADR-0002）。`logout` も同じで、待ちきれなければ削除せずにエラーにする。

`login` だけは、待ちきれなければ警告してロックなしで保存する。ブラウザでの操作を終えた利用者の
ログインを捨てないためである。このとき割り込んだ更新が古いログインの結果を書く可能性は残るが、
それは利用者がその場で見ていて、`login` をやり直せば済む。

### 5. 更新したことを記録する

更新に成功したとき、ほかのプロセスの更新結果を採用したときに、それぞれ stderr に 1 行ずつ出す。
トークンの値は出さない。更新のときは、サーバが新しい refresh token を返したかどうかも出す。
利用者がそのサーバの refresh token が使い捨てかどうかを自分で確かめられ、失敗したときに
「最後に更新できたのはいつか」「何本が更新しに行ったか」を後から追える。

## Consequences

- 同じサーバに何本の bridge が動いていても、期限切れのあとに更新しに行くのは 1 本だけになり、
  残りはその結果を採用する。使い捨ての refresh token を発行するサーバでも、保存済みのログインが失われない。
- ログインし直せば、動いている bridge は次の更新で新しいログインを拾う。MCP クライアントの再起動は要らない。
- ログアウトしたログインは、動いている bridge に書き戻されない。動いている bridge は、メモリ上の
  アクセストークンを、期限が来るまで（期限の無いトークンなら 401 を受けるまで）使い続ける。
  サーバ側でトークンを取り消す手段は、これまでどおり無い。
- ロックを持ったプロセスが止まったまま（デバッガで停止中など）だと、同じサーバへの要求は、
  更新が要る時点から 45 秒待ったあとエラーになり続ける。そのプロセスが動き出すか終われば直る。
- state ディレクトリに `tokens.json.lock` が増える。中身は空で、消されない。
- v0.3.0 以前の bridge はロックを取らない。更新後も古い bridge が動いている間は競合が残るので、
  同じサーバを使う MCP クライアントをすべて再起動する必要がある。リリースノートに書く。
- advisory lock は、ネットワークファイルシステム上の state ディレクトリでは効かないことがある。README に書く。
- Windows の `LockFileEx` は、実機では確かめられない（保守者の手元に Windows が無い）。クロスビルドと
  静的検査までで、そのことをリリースノートに書く。Windows では、別のプロセスが `tokens.json` を開いている
  間の置き換え（rename）が失敗し得る。`run` と `inspect` の読み込みはすべてロックの中で行うので、
  mcp-bridge どうしでは重ならない。ほかのプログラム（バックアップ、ウイルス対策など）が開いている間に
  重なった場合は保存の失敗になり、決定 2 の例外の扱いに入る（未確認）。
- ファイルロックの無い OS（aix、solaris など。配布対象ではない）では、ロックが使えない場合として扱う。
- 更新するたびに stderr に 1 行増える。1 プロセスあたり、アクセストークンの寿命（多くは 1 時間）に 1 回程度である。

## Alternatives considered

**`Token()` のたびにファイルの mtime を見て読み直す（ロックなし）。** 却下。放置したあとの一斉更新では、
全プロセスが読み直したあと同時に更新しに行くので、競合を防げない。決定 2 の読み直しは、ロックと組み合わせて
初めて効く。

**`invalid_grant` が返ったら、ファイルを読み直して 1 回だけやり直す。** 却下。reuse detection のあるサーバでは、
最初に使用済みのトークンを送った時点で grant が無効になっているので手遅れである。

**トークンの管理を 1 本の常駐プロセスに集める。** 却下。stdio と HTTP を橋渡しするだけという mcp-bridge の
狭い範囲（RFP）を大きく超える。ファイルロックで同じ効果が得られる。

**プロセスごとに別のトークンファイルを持つ。** 却下。ログインがプロセスごとに必要になる。

**同時に動く本数を減らす。** 却下。本数を決めるのは MCP クライアントで、利用者にも mcp-bridge にも制御できない。

**ロックが取れるまで際限なく待つ。** 却下。ロックを持つプロセスが止まっている（デバッガで停止中など）と、
同じサーバを使う全クライアントの要求が応答の無いまま止まる。

**上限まで待ったら、警告してロックなしで更新する。** 却下（設計の検証で見つかった）。待ちは前の保持者の分だけ
積み重なるので、上限を何秒にしても、応答の遅いサーバでは同じ refresh token を同時に送る場面が残る。

**ファイルが読めないときは、メモリ上の refresh token で更新する。** 却下。ファイルが無いのはログアウトの
結果であり、メモリ上の値で更新するとログインを書き戻す。壊れたファイルは `SaveTokens` の置き換えでは
生じず、手で編集された場合に限られるので、ログインし直しを案内する方が分かりやすい。

## Out of scope

- **refresh token を生かし続ける手段**（提案書の P3: `mcp-bridge refresh` サブコマンド、`run` の中の
  定期更新）。この ADR で競合を取り除いたあとも、長時間放置したあとの失敗が残るかどうかは、
  報告者が提案書 4.2 節の手順（どのプロセスも動かさずに 25 時間待って `inspect`）で切り分ける。
  残ると分かった場合に、ADR-0003 の「サーバを定期的に叩くことは却下」との関係も含めて、新しい ADR で扱う。
- どのクライアントにも延ばせない期限（Entra ID で redirect URI を SPA として登録した場合の 24 時間、
  条件付きアクセスによる再認証の要求）。セットアップガイドで扱う事柄であり、この ADR の対象ではない。

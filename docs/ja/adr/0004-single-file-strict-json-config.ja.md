# ADR-0004: 設定ファイルは1つ、strict decode、JSON

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-23 |
| Binds | mcp-bridge |
| Decision makers | nlink-jp maintainers |
| Triggered by | 前身ツールの設定が読み解けなくなり、実測した原因は分量ではなく構造だった |

## Context

mcp-bridge は、設定が追いにくくなった mcp-guardian から抽出された。新しい形を決める前に、
古い形を実測した。

- CLI フラグ 14 個。うち常用は 3 個
- profile キー 約26 個。うち使用は 5 個
- global config キー 約16 個。うち使用は 0 個——ファイル自体が存在しなかった

分量もその一部ではあったが、実害を与えていたのは構造上の欠陥である。

**規則の異なる2階層。** システムグローバルファイルがテレメトリと既定値を持ち、
サーバごとの profile が他のすべてを持っていた。profile は strict decode され、
グローバルファイルはされなかった。したがって同じ typo が一方のファイルでは致命的で、
他方では黙って無視された。

**読まれるタイミングの異なるキー。** `authorizeUrl` と `extraParams` は login コマンドだけが
消費し、実行時の設定構造体には決して到達しなかった。ファイル上には、
全セッションに適用されるキーとの区別を示すものが何もなかった。

**プロトコルと一致しない名前。** `transport: "sse"` が Streamable HTTP トランスポートを選択していた。
プロトコル改訂以降ずっと誤っていた名前である。

**直交する設定の結合。** `mask` は `enforcement` が `strict` のときだけ有効だったため、
ツールを隠すことが無関係なノブに黙って依存していた。

新規ツールに対する組織の規約は、`~/.config/<tool>/config.toml` の sectioned TOML と、
文書化された env 上書き優先順位である。

## Decision

**1ファイル・1つの形・strict decode。** `~/.config/mcp-bridge/config.json` が全設定を持つ。
第2階層もサーバごとのファイルも存在せず、すべてのキーが同じタイミングで適用される。
セッションまたはログインの開始時に、ファイル全体が読まれ、まとめて検証される。
`XDG_CONFIG_HOME` がベースディレクトリを変更し、これはテストスイートが
開発者の実設定と実トークンに触れないための仕組みでもある。

**組織規約の sectioned TOML ではなく JSON。** これは意図的な規約逸脱である。TOML パーサは
外部依存であり、mcp-bridge は OAuth の client secret とアクセストークンを扱う。
`go.mod` の require 行をゼロに保つことで、資格情報の経路にサードパーティのコードが入らない。
JSON は周辺の MCP エコシステムが既に使っている形式（`.mcp.json`、`claude.json`）とも一致し、
`encoding/json` は strict decode を直接サポートする。

**未知のキーはエラー。** 単一ファイルに `DisallowUnknownFields` を適用する。
手書きの設定は typo を溜める。`callbackScheme` に対する `callbackSchema` は、
画面上に何の説明も出ないまま黙って発動しない機能になる。

**認証は mode 文字列ではなくキーの存在で選ぶ。** `flow` キーも `transport` キーもない。
`oauth` があって中身が埋まっていれば事前登録クライアント、`"oauth": {}` なら discovery、
`tokenCommand` なら外部コマンド、`headers` だけなら静的な資格情報、いずれもなければ認証なし。
`mode` フィールドは、隣のブロックと食い違い得る第2の真実になる。

**問題はすべて一度に報告する。** 検証は最初の失敗で止まらず全件を集める。
ファイルが目の前で開かれているときに、1回の実行で1つずつ直させるのは不要な作業だからである。

## Consequences

- 本ツールは組織の TOML 規約に従わない。これは実際のコストである。
  他のツールを知っている利用者は差異に気づく必要がある。両 README は形式を導入する箇所で理由を述べている。
- 設定にコメントを書けない。代わりに両 README の例が説明を担う。
- 設定パスと OAuth コールバックポート以外、実行ごとに設定できるものはない。これは意図的である。
  前身ツールのフラグ面こそが、モードを見えにくくしていた当のものだった。
- 後から真にグローバルな設定を追加するには新たな判断が要る。現時点でそうした階層に置くものはない。
  以前それを埋めていたテレメトリはスコープ外である。

## Alternatives considered

**`BurntSushi/toml` による sectioned TOML**（組織規約に従う）。却下。仕事の全体が資格情報に関わる
ツールにおける依存追加のため。コメントが書けることは本物の利得だった。

**TOML サブセットの自前パーサ**（規約と依存ゼロの両立）。却下。コメント対応と引き換えに、
妥当だが一般的でない TOML に対する失敗モードを自分たちで背負う約150行のパーサを抱えることになる。

**グローバルファイルを持つ2階層構成の維持。** 却下。テレメトリを落とした後、
グローバル階層に置くものが何も残らず、その階層こそが前身ツールを分かりにくくしていた要因の半分だった。

**前身ツールと同様、ディレクトリ内のサーバごとファイル。** 却下。サーバが数個の規模では、
読める1ファイルを複数に分割するだけであり、しかもそれは login 時のキーと実行時のキーが
気づかれずに混ざることを許した構成そのものだった。

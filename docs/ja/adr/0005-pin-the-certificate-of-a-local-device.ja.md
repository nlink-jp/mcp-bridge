# ADR-0005: 検証できない証明書の機器は、無条件に信用せず証明書を固定する

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-11-09 |
| Binds | mcp-bridge |
| Decision makers | nlink-jp maintainers |
| Triggered by | ローカルネットワーク上の機器に組み込まれた MCP サーバの証明書を、通常の検証が拒否する |

## Context

mcp-bridge は上流の TLS 証明書を Go の既定どおりに検証し、それを変える手段を持たない。
ローカルネットワーク上の機器は、この検証に通らないことが多い。

きっかけは NanoKVM である。実機で測った証明書は自己署名で、発行先は `localhost`、
`127.0.0.1`、`::1` であり、ネットワーク上でその機器に到達するときの名前を含まない。
発行者を保証する者がいないことと、名前が一致しないことの、独立した 2 つの検査に落ちる。

2 つ目の失敗により、よくある解決策は使えない。追加の CA ファイルを信頼しても直るのは
発行者の検査だけで、名前は一致しないままなので、接続は拒否され続ける。

この接続で何が運ばれるかも重要である。KVM 機器の資格情報は、接続先のマシンの操作権そのもの
であり、全リクエストのヘッダで送られる。

## Decision

**サーバごとに、提示してよい証明書を 1 つ指定できるようにする。** 省略可能なサーバ単位のキー
`tlsCertSha256` に、サーバ証明書の SHA-256 指紋を 16 進で書く。コロンの有無と大文字小文字は
問わない。`openssl x509 -fingerprint -sha256` が出力する値と同じ形である。

**固定は検証を置き換えるものであり、上乗せではない。** このキーがあるとき、提示された証明書は
固定したものとバイト単位で一致しなければならず、その比較が検査のすべてである。発行者、
ホスト名、有効期間は調べない。調べれば、まさに対象としている機器を拒否してしまうし、
証明書の完全一致は、それらの検査が代わりに確かめようとしていることに既に答えている。
したがって、固定した証明書は有効期限を過ぎても動き続ける。

**不一致は TLS ハンドシェイクの時点で接続を止める。** リクエストを送る前なので、ヘッダや
トークンがなりすましに届くことはない。エラーには提示された指紋と設定された指紋を示す。
証明書を意図して作り直したときは、値の差し替えが対処だからである。

**`https` から外れるリダイレクトは拒否する。** Go は同じホストへのリダイレクトでは、スキームに
関係なくリクエストのヘッダを引き継ぐ。そのため、`http` へリダイレクトするよう誤設定された機器が
あると、資格情報が平文で送られてしまう。別の `https` サーバへのリダイレクトは固定の検査で
落ちるので、規則を設ける必要はない。

**このキーは、MCP エンドポイントへの接続すべてに効く。** `run`、`inspect`、`inspect` 内の
無認証の確認の 3 つである。最後の 1 つが漏れると、確認が証明書で失敗し、`inspect` は
試していない資格情報を「受理された」と報告してしまう。

**次の 2 つの組み合わせは設定エラーとする。** いずれも、どこかでキーが黙って無視されることに
なるためである（ADR-0004）。

- `http` の URL には、比較する証明書が無い。
- `oauth` のログインは、別ホストであることが多い認可・トークンエンドポイントと通信するので、
  固定を適用できない。対象の機器は静的ヘッダかトークンコマンドを使う。

## Consequences

- 機器が証明書を作り直すと、設定を更新するまで接続できなくなる。これは意図したトレードオフ
  である。なりすましが起きたときも同じ失敗になり、両者を見分けるのは操作者の判断である。
- 最初の指紋はどこかから得る必要がある。操作者が信頼できるネットワークで読み取ることが、
  固定に意味を持たせる。コマンドは README に記載する。mcp-bridge が指紋を記録する機能は
  持たない。最初に見たものを信じるツールは、判断を操作者から取り上げることになる。
- この版より古い mcp-bridge は、このキーを未知のキーとして拒否し、ファイル全体を読み込めなく
  なる（ADR-0004）。そのため、更新が先で、設定の変更が後である。
- `HTTPS_PROXY` が `https://` のプロキシを指していると、プロキシ自身の証明書が固定と比較され、
  接続は失敗する。安全側に失敗し、ローカルネットワークの機器をそのようなプロキシの背後に置く
  理由も無いので、対処せず許容する。`http://` のプロキシは TLS を中継するだけなので影響しない。
- 空の `"tlsCertSha256": ""` は未設定として扱う。通常の検証が働くので、固定が必要な機器は
  見える形で失敗する。両者を区別するためにフィールドの表現を増やす価値はない。
- 通信は HTTP/1.1 のままである。独自のダイアラを設定している時点で Go の HTTP/2 自動有効化は
  既に無効であり、TLS 設定を加えても変わらない。

## Alternatives considered

**検証を無効にするスイッチ（`insecureSkipVerify`）。** 指紋が不要で、証明書の作り直しにも
影響されない。却下: ローカルネットワークでその機器の名前を騙れる者なら誰でも資格情報を
受け取れてしまい、この種の機器ではそれが別のマシンの操作権になる。固定のコード量はほぼ同じで、
増えるのは設定時の 1 手順だけである。

**サーバごとの CA ファイル。** 上記の実測により、今回の解決策としては却下。発行者の検査は
直るが名前の不一致が残る。正しい名前で発行するプライベート CA には適するが、それは別の場面で
あり、現れたときに判断すればよい。

**スイッチと固定の両方を用意する。** 却下: mcp-bridge は使われない選択肢が前身を読み解けなく
した経緯から生まれており（ADR-0004）、必要は 1 つの仕組みで満たせる。

**OAuth のエンドポイントにも固定を適用する。** 却下: 別ホストの認可サーバは別の証明書を提示
するので 1 つの固定では両方を賄えず、両者を組み合わせる機器も見当たらない。

# ADR-0003: refresh を持たないトークンに、対処可能な期限は存在しない

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-23 |
| Binds | mcp-bridge |
| Decision makers | nlink-jp maintainers |
| Triggered by | Slack はトークンローテーション無効時に `expires_in` も refresh token も返さない。これを期限として扱うと毎時間の再ログインを強いる |

## Context

OAuth のトークン応答は `expires_in` を省略することも、`refresh_token` を省略することも、
両方を省略することもある。この組み合わせが重要なのは、クライアントに何ができるかを決めるためである。

| `expires_in` | `refresh_token` | クライアントにできること |
|--------------|-----------------|------------------------|
| あり | あり | 失効前に更新する |
| なし | あり | 定期的に確認する。更新手段はある |
| あり | なし | 何もない。失効したら新規ログインのみ |
| なし | なし | 何もない。対処すべき期限が存在しない |

最後の行がトークンローテーション無効時の Slack のケースであり、
ローテーションを明示的に有効化していない Slack アプリの既定である。
2026-08-23 に実 Slack MCP サーバで検証した。新規ログインはどちらのフィールドも返さず、
3ヶ月前に保存され記録上の期限をとうに過ぎたトークンも Slack に受理された。

前身ツールはこの種のトークンに人為的な1時間の期限を保存し、その後の使用を拒否していた。
結果として、サーバがまったく問題としていない資格情報に対して、毎時間の再ログインを要求していた。

## Decision

`expires_at == 0` は **「期限が分からない」** を意味し、「エポック時点で失効済み」ではない。

refresh token を持たないトークンは、記録された期限が何を言っていようと保存されたまま返す。
mcp-bridge にはその期限に対してできることが何もない。更新経路が存在しないため、
ローカルでトークンを拒否しても、動いているセッションを失敗したセッションに置き換えるだけである。
判定するのはサーバであり、その判断は 401 として届く。

refresh token がある場合は期限を尊重し、自動で更新する。確認と、それを使うリクエストとの間に
トークンが失効しないよう、わずかなマージンを取る。

ログイン時、保存する期限は次のように決める:

- `expires_in` あり → それに従う。
- `expires_in` なし・refresh token あり → 1時間後に再確認する。更新手段があるので推測のコストはゼロ。
- どちらもなし → 0 を保存する。

使用可能な資格情報を残さない 401 は、拒否された事実と代替が存在しない理由の両方を載せ、
ログインコマンドを名指しして報告する（ADR-0002）。

## Consequences

- 期限のない Slack トークンは、Slack がそれを認める限り動作し、定期的な再ログインを必要としない。
- 本当に失効したトークンは、401 が返るまでに1回だけ余計に使われる。
  生きている資格情報を決して拒否しないことと引き換えの、1リクエストの無駄である。
- この種のトークンの `expires_at` は情報を持たない。省略ではなく 0 を書くことで、
  「遠い過去に失効した」との区別をファイル上で明示する。

## Alternatives considered

**プロバイダが期限を示さない場合は1時間を既定とする。** 却下。これは前身ツールが行っていたことであり、
本 ADR はそれを取り消すために存在する。期限のない資格情報を毎時間の中断に変える。

**どちらのフィールドもないトークンの保存を拒否し、ローテーションを必須とする。** 却下。
ローテーションは利用者が制御できるとは限らないプロバイダ側の設定であり、しかもトークンは動作する。

**失効を早期に検知するためサーバを定期的に叩く。** 却下。次の実リクエストがどうせ発見することを
発見するためにトラフィックを増やすだけで、失効トークンへの対応はいずれにせよ同じ——再ログイン——である。

# ADR-0002: 転送できなかったリクエストには必ず応答する

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-23 |
| Binds | mcp-bridge |
| Decision makers | nlink-jp maintainers |
| Triggered by | 失敗時に沈黙するブリッジはクライアントを自身のタイムアウトまでブロックさせ、多くの場合1コマンドで直る原因を隠す |

## Context

中継器は、応答を期待するクライアントと、到達不能・未認証・故障し得るサーバの間に立つ。
転送が失敗したとき選択肢は2つある。何も言わないか、失敗したリクエスト宛の
JSON-RPC エラー応答を合成するかである。

何も言わないのは魅力的な既定に見える。ブリッジ自身が失敗を生んだわけではなく、
応答を捏造するのは越権に感じられる。しかしこれは誤った選択である。JSON-RPC クライアントは
id で応答を対応付けており、他に手がかりを持たない。応答のないリクエストは
クライアント自身のタイムアウト——通常は数十秒——までブロックし、
「サーバが応答しなかった」ことしか報告しない。

実際の原因は具体的で対処可能である。OAuth トークンの期限切れ、失効、ネットワーク障害、
URL の設定ミス——いずれも見る価値のあるメッセージを持ち、最初の2つは
`mcp-bridge login` 1コマンドで直る。ブリッジが黙ればそのすべてが失われる。

## Decision

転送できなかったクライアントの**リクエスト**には、送られてきた id と、
根本原因をメッセージとして載せた JSON-RPC エラー応答を必ず返す。
これは mcp-bridge が自ら生成する唯一のメッセージ種別であり、他はすべて無改変で中継する。

これを健全に保つ3つの規則がある。

**Notification には決して応答しない。** id を持たず、notification への応答はプロトコル違反である。
失敗は代わりに stderr へ記録する。

**原因は経路全体を通じて残す。** 401 が使用不能な資格情報につながった場合、
「拒否された」と「代替が存在しない理由」の両方を報告する。連鎖の最後のエラーだけを出さない。
これは失効トークンで実 Slack MCP サーバに対して実行して発見された。メッセージが
「no access token」まで劣化しており、これは拒否された資格情報を無効化した後の結果であって、
トークンファイルが空であるかのように読めた。

**二重応答をしない。** ハンドラは応答を書くか、応答に変換されるエラーを返すかのいずれかで、
両方を行わない。

パース不能な入力には null id を載せた parse error を返す。id はパースできなかった
メッセージの中にあるためである。

## Consequences

- クライアントは、数十秒後のタイムアウトではなく、リクエストが失敗した瞬間に
  表示可能なエラーを受け取る。
- mcp-bridge はサーバが送っていないメッセージを出力する。それらは常にエラーであり、
  常に特定のリクエスト宛であり、決して result ではない。したがってクライアントが
  データと取り違えることはない。
- エラー文言はクライアントに届くため、秘密情報を含めてはならない。
  メッセージが名指しするのはエンドポイント・ステータスコード・コマンドであり、トークンではない。

## Alternatives considered

**沈黙してクライアントのタイムアウトに任せる。** 却下。診断情報が失われ、待ち時間が長い。
これが隠す失敗モードは、いずれもよく起きるものである。

**転送失敗時に接続を閉じる。** 却下。リクエスト単位の回復可能なエラーを、死んだセッションに変える。
クライアントは認証の問題ではなくクラッシュとして報告する。

**汎用の「upstream unavailable」を返す。** 却下。失効トークン・ネットワーク障害・不正 URL の
区別を捨てることになる。その区別こそがメッセージの価値のすべてである。

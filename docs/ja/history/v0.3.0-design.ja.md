# v0.3.0 設計メモ: Entra ID で保護された MCP サーバへの接続

2026-11-17 時点の設計の記録である。判断とその理由は
[ADR-0006](../adr/0006-discovery-with-a-pre-registered-client.ja.md) にある。この文書は、
要求、部品ごとの約束と手順、テストの判定基準、作業の順序を定める。リリース後は更新しない。

## 1. 要求

利用者からの報告（Microsoft Agent 365 の MCP サーバに接続できない）を、確認のうえ次の要求にした。

| # | 要求 |
|---|------|
| R1 | リダイレクト先が `http://localhost:<port>/callback` で登録されたクライアントでログインできる |
| R2 | `clientId` と待ち受けの設定だけを書いた構成で、認可・トークンエンドポイントをサーバの公開情報から決め、動的登録を行わない |
| R3 | Entra ID の認可サーバのメタデータを取得できる |
| R4 | MCP サーバが示すスコープを要求する |
| R5 | Entra ID から更新トークンを得られる |
| R6 | 同じ `clientId` と同じポートを使う複数のサーバを、順にログインし、同時に `run` できる |
| R7 | 開発側が相手を観測できないので、利用者が貼り付けた `login` の出力だけで、どこで何が決まったかが分かる |
| R8 | 既存の設定（URL を全部書いた構成、`"oauth": {}`）は、書き換えなしで動く |

R6 は現状で満たしている（`run` はポートを使わない）。変更で壊さないことをテストで固定する。

### 範囲外

- リダイレクト先のパスの設定（ADR-0006 で見送り）。
- `resource` パラメータの付与、認可サーバが PKCE 対応を公開しているかの確認、`issuer` の検証、
  `prompt=consent` の付与（ADR-0006「これまでどおり行わないこと」）。
- 設定の `url` を書き換えたあと、再ログインせずに使った場合の扱い。保存済みのトークンは
  書かれた `url` へ送られる。静的ヘッダやトークンコマンドと同じく、接続先は設定を書いた人が決める。
- 更新要求の形。`grant_type` と `refresh_token`（と `client_id`）のままとする。Entra ID の文書は
  更新要求の `scope` を省略可としている。

## 2. 部品と流れ

変更するのは次の部品である。新しい部品は作らない。

| 部品 | 場所 | 担う要求 |
|------|------|----------|
| 設定の検証 | `internal/config` | R1, R2, R8 |
| コールバックの待ち受け | `internal/oauth`（`startCallbackServer`） | R1 |
| 探索 | `internal/oauth`（`discover` とその下） | R2, R3, R4, R5, R7, R8 |
| 通信の共通設定と表示 | `internal/oauth`（HTTP クライアント）、`internal/cli`（設定の受け渡し、`run` の読み取り） | R2, R6, R7 |

`login` の流れは次のとおり。太字が今回変わる所である。

1. 設定を読み、検証する。**（`callbackHost`、URL を省いた構成）**
2. コールバックを待ち受ける。**（ホスト名、`::1`）**
3. 設定に URL が無ければ探索する。
   1. MCP サーバに未認証の要求を送り、401 応答を読む。**（`scope` も読む）**
   2. MCP サーバのメタデータを取得する。**（well-known の 2 か所、`resource` の確認、`scopes_supported`）**
   3. 認可サーバのメタデータを取得する。**（3 か所目）**
   4. クライアントを決める。**（`clientId` があれば登録しない）**
   5. スコープを決める。**（順序、`offline_access`）**
   6. 結果を保存し、表示する。**（出所の表示、`url` の記録）**
4. ブラウザで認可し、コードをトークンに交換し、保存する。（変更なし）

`run` は保存された結果からトークンエンドポイントを読む。変えるのは 1 点だけである（3.4）。

R8 について。URL を全部書いた構成は探索を通らないので、動きは変わらない。`"oauth": {}` は
探索を通るので、ADR-0006 の Consequences に挙げた 4 つの変化を受ける。

## 3. 詳細設計

### 3.1 設定の検証

**入力:** `oauth` ブロック。新しいキーは `callbackHost`（文字列、省略可）だけである。

**規則:** ブロックが空（`{}`）なら検証しない（従来どおり、探して登録する）。空でなければ次を
すべて調べ、問題をまとめて報告する。新しい規則に ★ を付けた。

| 条件 | 結果 |
|------|------|
| `clientId` が無い | エラー（従来どおり） |
| ★ `authorizeUrl` と `tokenUrl` の片方だけがある | エラー。両方書くか両方省くかを示す |
| ★ URL を両方省き、`clientSecret` がある | エラー。シークレットを使うなら URL を書くよう示す |
| ★ `callbackHost` が `""`・`"127.0.0.1"`・`"localhost"` のいずれでもない | エラー |
| URL が `https` でない、ポートが範囲外、`callbackScheme`・`clientAuthMethod` の値や組み合わせが不正 | エラー（従来どおり） |

`callbackHost` だけを書いたブロックは空ではない（`clientId` が要る）。URL を省いた構成で
`clientAuthMethod` が `basic` のときは、従来の規則（`basic` はシークレットが要る）がエラーにする。

**出力:** `callbackHost` を書かないときの値は、`callbackScheme` が `https` なら `localhost`、
それ以外は `127.0.0.1`。`callbackScheme: "https"` と `callbackHost: "127.0.0.1"` の組み合わせは
許す（証明書は両方の名前を含む）。

**表示上の方式名:** `list` と `inspect` が出す方式名は増やさない。`clientId` を書いた構成は、
URL の有無によらず `oauth` と表示する。

### 3.2 コールバックの待ち受け

**入力:** ホスト名、ポート（0 は OS に任せる）、スキーム。

**手順:**

1. `127.0.0.1:<port>` で待つ。失敗したら従来どおりのエラーで終わる。
2. ホスト名が `localhost` のとき、決まったポートで `[::1]` でも待つ。
   - 待てたら、両方で同じ応答を返す。
   - 待てなかったら、`[::1]:0` で待てるかを試す。これも失敗するなら、その機械に IPv6 の
     ループバックが無いので、何も表示せず `127.0.0.1` だけで続ける。`[::1]:0` では待てるなら、
     そのポートが他で使われているので、次の 1 行を表示して続ける:
     「`[::1]:<port>` で待てなかった。認可のあとブラウザに mcp-bridge の完了画面が出なかったら、
     アドレス欄の `localhost` を `127.0.0.1` に書き換えて開き直す」。
     ブラウザが `::1` 側の別のプロセスに繋がった場合も、繋がらなかった場合も、同じ対処で届く。
3. スキームが `https` なら、両方のリスナーを同じ証明書で TLS にする（証明書は従来どおり）。
4. リダイレクト先は `<scheme>://<host>:<port>/callback`。

**出力:** リダイレクト先の文字列と、コードを待つ口。終了時にすべてのリスナーを閉じる。

### 3.3 探索

**入力:** MCP サーバの `url`、リダイレクト先、設定の `clientId`（空なら動的登録する構成）、
保存場所。

**出力:** 認可エンドポイント、トークンエンドポイント、クライアント（動的登録したときだけ）、
スコープとその出所。

**使い回し:** `clientId` があるときは、保存済みの結果を使わず毎回探す。`clientId` が無いときは、
保存済みの結果の `url` とリダイレクト先がどちらも今回と一致し、クライアントが記録されている
場合に限って使い回す。`url` の記録が無い古い保存結果は使い回さない。

**手順 1 — 401 応答を読む。** 未認証の `initialize` を送る（従来どおり）。401 のとき、
`WWW-Authenticate` から `resource_metadata` と `scope` を取り出す。401 でないときと、
`resource_metadata` が無いときは、手順 2 の well-known へ進む。サーバから応答が得られなかった
ときは、そこでエラーにして終わる。他の候補も同じホストにあり、同じ失敗を繰り返すだけだからである
（実物での確認で、接続できないだけの場面が「公開情報が無い」と案内されるのを見て改めた）。

読み取りは、文字列の検索ではなく、ヘッダの書式（RFC 9110 §11.2 の方式名とパラメータの並び）に
沿って行う。方式名とパラメータ名は大文字小文字を区別しない。値は引用符つき（`\` による
エスケープを解く）と引用符なしの両方を読む。ヘッダが複数行あるときは、順に見て最初に `Bearer`
方式でその名前を持つものを採る。書式に合わない行は読み飛ばす。1 つのチャレンジに同じ名前の
パラメータが 2 度ある行も、書式に合わないものとして読み飛ばす。空か空白だけの値は無いものとして
扱う。

**手順 2 — MCP サーバのメタデータ。** 候補を順に取得し、最初に使えたものを採る。

1. 401 応答の `resource_metadata` の URL（あれば、これだけを試す）
2. `<origin>/.well-known/oauth-protected-resource<url のパス>`（`url` にクエリがあれば付ける。
   パスが `/` だけなら 3 と同じなので試さない。RFC 9728 §3.1）
3. `<origin>/.well-known/oauth-protected-resource`

使える条件は、JSON として読め、`authorization_servers` が 1 つ以上あり、`resource` が `url` と
一致することである。一致とは、スキームとホストが大文字小文字を区別せず同じで、ポートが同じ
（書かれていなければスキームの既定のポート）で、`resource` のパスが `url` のパスの先頭に
区切り単位で一致すること（末尾の `/` の有無は区別しない。`/mcp` は `/mcp/x` に一致し、
`/mcpx` には一致しない）。パスは書かれたままの形で比べ、`%2F` は区切りとして扱わない。
クエリは比べない。利用者情報（`user@`）を含む `resource` は一致としない。

`resource` が無いものは使わず、次の候補へ進む。`resource` が一致しないときは、他の候補を
試さずにエラーで終わる。エラーは両方の値と、サーバの公開情報が `url` と食い違っていることを示す。
認可サーバは `authorization_servers` の先頭を使う（従来どおり）。

**手順 3 — 認可サーバのメタデータ。** issuer にパスがあるとき、次の順に試す。

1. `<origin>/.well-known/oauth-authorization-server<パス>`
2. `<origin>/.well-known/openid-configuration<パス>`
3. `<issuer>/.well-known/openid-configuration`（今回追加）

パスが無いときは 1 と 2 だけである。使える条件は、認可・トークンの両エンドポイントがあること
（従来どおり）。

**手順 2・3 が失敗したとき。** 従来どおり、`url` のホスト自身を issuer として手順 3 を試す。
すべて失敗したら、試した場所と結果を並べたエラーで終わる（従来どおり）。エラーが案内する
対処は構成で変える。`clientId` があるときは「`authorizeUrl` と `tokenUrl` を書く」、
無いときは従来の文言である。

**URL の条件。** 探して得た URL（メタデータの URL、issuer、認可・トークン・登録の各エンドポイント）は、
`https` である場合だけ使う。設定の `url` が `http` のときに限り、`http` の URL も使う。
条件に合わない URL は、その候補を失敗として扱い、理由を試行の一覧に載せる。

**手順 4 — クライアント。** `clientId` があれば登録しない。無ければ従来どおり登録し、
登録口が無ければ従来のエラーで終わる。

**手順 5 — スコープ。** 探索が返すスコープは、最初に得られたものである。

1. 401 応答の `scope`
2. MCP サーバのメタデータの `scopes_supported`
3. 認可サーバのメタデータの `scopes_supported`
4. 無し

1 か 2 で決まり、認可サーバの `scopes_supported` に `offline_access` があり、決まったスコープに
`offline_access` が無いとき、末尾に足す。設定に `scopes` があるときは、探索の結果ではなく
設定の値が使われる（従来の重ね合わせの規則どおり）。

**手順 6 — 保存と表示。** 結果に `url` を加えて保存する。`login` は、探索を行ったときに限り、
次を表示する。

- 認可サーバ（issuer）と、それを示したメタデータの URL
- クライアントの扱い（設定のものを使う／登録した）
- 要求するスコープと出所（設定／サーバの 401 応答／サーバのメタデータ／認可サーバのメタデータ／
  無し）。`offline_access` を足したときはそのことも

以前の登録を使い回すときは探索をしていないので、従来の 1 行（使い回す旨）に加えて、スコープを
「保存済みの登録のもの」として表示する。トークン、シークレット、認可コードは表示しない
（従来どおり）。

**上限。** メタデータの読み取りは 1 件 1 MiB まで、通信は 1 回 30 秒まで（従来どおり）。
探索が行う要求は、多くて 401 の確認 1 回、MCP サーバのメタデータ 2 回、認可サーバのメタデータ
3 回、従来の経路 2 回、登録 1 回である。

### 3.4 通信の共通設定、表示、`run` の読み取り

**リダイレクト。** ログインと更新に使う HTTP クライアントは、`https` の URL から `https` 以外への
リダイレクトに従わず、エラーにする。`http` から始まった通信（設定の `url` が `http` の場合）も、
途中で `https` に入ったあとは同じである。それ以外は Go の既定に従う。回数の上限は Go の既定
（10 回）である。従わなかったリダイレクトは「サーバは応答した」として扱い、手順 1 では
well-known へ進む。

**表示の無害化。** `login` の表示と、探索・ログインが返すエラーには、サーバが返した文字列
（issuer、スコープ、URL、エラーの説明）が入る。端末に書く直前の 1 か所で、改行とタブ以外の
制御文字と、双方向制御文字を取り除く。対象は `login` の出力全体と、コマンドが最後に表示するエラーである。
`inspect` の出力と `run` のログも、サーバが返した内容を表示するので、同じ所を通す。
`run` が中継する JSON-RPC の本文には手を入れない。

**設定の受け渡し。** `callbackHost` を、設定からログインの処理へ渡す。

**`run` の読み取り。** 保存結果のトークンエンドポイントには、探索のときと同じ「URL の条件」を
当てる。旧版は検査せずに保存していたので、条件に合わないものは使わず、ログインし直すよう
案内して終わる。保存結果からクライアントのシークレットを取るのは、クライアントの ID も
保存結果から取った場合に限る。`"oauth": {}` を `clientId` だけの構成に書き換えて再ログイン
しなかったとき、以前の動的登録のシークレットを設定の `clientId` と組にして送らないためである。

## 4. テストの設計

期待値を決めるものを、テストごとに決めておく。

| 対象 | 確かめること | 期待値を決めるもの |
|------|--------------|--------------------|
| 設定の検証 | 3.1 の表の各行、既存の設定例がそのまま通ること | 3.1 の表 |
| 待ち受け | ホスト名とスキームの 4 通りのリダイレクト先。`localhost` のとき `127.0.0.1` と `::1` の両方で応答すること。`::1` のポートが塞がっているときに 1 行を表示して続くこと | 3.2 の手順 |
| 401 応答の読み取り | `scope` と `resource_metadata` の取り出し。引用符の有無、名前の大文字小文字、複数行、空の値、`error_description` 内の文字列を拾わないこと、書式に合わない行（表テスト） | RFC 9110 §11.2 と RFC 6750 §3 の書式 |
| メタデータの候補 | 401 応答に URL が無いとき・401 でないときの 2 か所、クエリつきの `url`、`resource` の一致・不一致・欠落（比較は表テスト: 既定ポート、大文字小文字、末尾の `/`、区切りをまたがない一致） | 3.3 手順 2、RFC 9728 §3.1 |
| 認可サーバの場所 | 3 か所目にだけ文書がある issuer で取得できること | Entra ID の実測（2026-11-17: 1・2 は 404、3 は 200） |
| スコープ | 4 段の順序と `offline_access` の条件（純粋な関数の表テスト） | 3.3 手順 5 |
| URL の条件 | `url` が `https` のとき `http` の先を使わないこと、`url` が `http` のとき使うこと | 3.3「URL の条件」 |
| リダイレクト | `https` から `http` へのリダイレクトに従わないこと（メタデータの取得とトークン要求） | 3.4 |
| 表示の無害化 | サーバが返した文字列の制御文字が、`login` の出力とエラーに出ないこと | 3.4 |
| 設定の優先 | 設定に `scopes` があるとき、その値だけを要求し `offline_access` を足さないこと | 3.3 手順 5 |
| 設定の受け渡し | 設定の `callbackHost` がログインの処理に渡ること | 3.4 |
| Entra ID 形の通し | 下記の疑似サーバに対して `clientId` だけの構成でログインし、認可 URL のクエリ（`client_id`・`scope`・`redirect_uri`）、登録要求が 0 回であること、トークン要求に `client_secret` が無いこと、保存結果の内容 | 3.3 全体と、Entra ID の公開メタデータの実測値 |
| 使い回し | `clientId` があると 2 回目のログインも探し直すこと。`clientId` が無いとき、`url` が違う保存結果と古い保存結果を使い回さないこと | 3.3「使い回し」 |
| `run` の経路 | 設定の `clientId` と保存結果のトークンエンドポイントで更新要求が出ること。保存結果に以前の動的登録のシークレットが残っていても送らないこと | 2 章の流れ、3.4 |
| 複数サーバ（R6） | 同じ `clientId`・同じポートの 2 つのサーバに順にログインでき、保存結果がサーバごとに分かれること。`run` の経路がポートを使わないこと | R6 |
| 文言 | `clientId` がある構成のエラーに「動的登録」の案内が出ないこと、表示にトークンが出ないこと | 3.3 手順 2・6 |
| 互換 | 既存のテストが、次の 1 件以外は書き換えなしで通ること。設定の検証の「`clientId` だけのブロックはエラー」という期待は、この設計で逆になる | R8 |

**Entra ID 形の疑似サーバ。** テスト内に立てる。MCP サーバは 401 と `resource_metadata` を返す。
メタデータは `resource`、パスつきの issuer、API のスコープを返す。認可サーバの文書は 3 か所目に
だけ置き、他は 404 にする。文書の中身は Entra ID の公開メタデータに合わせる（登録口なし、
`scopes_supported` は `openid profile email offline_access`、認証方式の一覧に `none` が無い、
`code_challenge_methods_supported` が無い）。

**実物での確認（リリース前、手で行う）。** Entra ID のテナントは無いが、次は実物で確かめられる。

1. 実際の Entra ID のメタデータ取得と認可 URL の組み立て。手元に立てた疑似の MCP サーバが
   `https://login.microsoftonline.com/common/v2.0` を認可サーバとして示し、仮の `clientId` で
   `login` する。ブラウザが Entra ID の画面まで進み、クライアントが見つからない旨のエラーに
   なれば、そこまでは正しい。
2. 実在の MCP サーバでの探索。GitHub の MCP サーバ（メタデータを公開し、登録口が無い）に対して
   `clientId` だけの構成で `login` し、探索の表示が GitHub の公開内容と一致することを見る。

## 6. テナントでの実行（リリース後）

2026-11-17 に、報告した利用者が自分のテナントの Microsoft Agent 365 のサーバ（`mcp_MailTools`）に
対して v0.3.0 を実行し、出力と自分で測った結果を送ってくれた。テナント ID とクライアント ID は
伏せてある。`oauth` ブロックに書いたのは `clientId`、`"clientAuthMethod": "none"`、
`"callbackHost": "localhost"`、`"callbackPort": 8080` だけである。

**動いたこと。** 初回のログイン。`inspect`（`Microsoft.MCPPlatform.WebApi 0.1.3604.4207`、
プロトコル `2025-06-18` から 22 個のツールを取得し、`oauth (credential accepted)` と表示）。
更新トークンによる更新。

**サーバが未認証の要求に返すもの** — 4 章で確かめられなかった応答である。

- トークンなしの `initialize`: `401`、本文は空、
  `WWW-Authenticate: Bearer resource_metadata="https://agent365.svc.cloud.microsoft/.well-known/oauth-protected-resource/agents/tenants/<tenant-id>/servers/mcp_MailTools"`。`scope` パラメータは無い。
- ホスト直下の `/.well-known/oauth-protected-resource`: `400 EndpointInvalid`。
- challenge が示した文書（`200`）:

**ログインの出力。**

**更新。** `tokens.json` の `expires_at` を過去の時刻に書き換えると、`inspect` は `scope` を
付けない更新要求を送った。Entra ID は新しいアクセストークンと新しい更新トークンを返し、
両方が保存され、サーバは新しいトークンを受け付けた。

**設計と照らした結果。**

| 設計 | 観測 |
|------|------|
| 3.3 手順 1: 401 を読み、`resource_metadata` をたどる | challenge がメタデータの場所を示したので、well-known の場所は推測していない。ホスト直下の場所は 400 を返す |
| 3.3 の `resource` の確認（パスの先頭一致） | `resource` は `url` と完全に一致した。完全一致の規則でも通っており、先頭一致はここでは要らなかった |
| 認可サーバの文書は 3 か所目、`issuer` は置き換え前の文字列 | サーバが示すのは `organizations/v2.0`。公開されている文書は issuer の後ろに付けた場所にあり、`issuer` は common と同じく `{tenantid}` を含む。表示はサーバが示した issuer になっている |
| スコープは challenge、次にサーバのメタデータ | サーバのメタデータから決まった。スコープはサーバの URL に `/.default` を付けたものと、`openid profile offline_access` |
| 認可サーバの一覧にあれば `offline_access` を足す | 働いていない。サーバの一覧にはじめから入っているので何も足されず、表示は「from the server's metadata」だけである |
| `resource` パラメータなし、PKCE 対応の公開の確認なし、`issuer` の確認なし | 3 つとも行わないままログインが完了した |
| 更新要求に `scope` を付けない | 受け付けられた。この更新で新しい更新トークンが返り、保存済みのものと置き換わった |

**疑似サーバとの違い。** 4 章の疑似サーバは公開文書から作った。テナント専用の認可サーバを示し、
メタデータを独自のパスで返し、`offline_access` を含まない `api://` のスコープを 1 つだけ並べる。
どれも判断を変えるものではない。`TestLoginAgainstWhatAgent365Publishes` が、観測した形を
その隣に加えている。

**まだ観測していないこと。** `mcp_MailTools` 以外の Agent 365 のサーバと、その 2 つが
クライアントとポートを共有する場合。`offline_access` を足す規則が Entra ID に対して働く場合。
`resource` パラメータを `scope` と一緒に送ったときの Entra ID の応答。Agent 365 ではない、
Entra ID で保護されたサーバ。

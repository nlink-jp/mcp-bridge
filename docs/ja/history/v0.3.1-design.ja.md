# v0.3.1 設計メモ: 同時に動く bridge のあいだでトークンの更新を 1 本ずつ行う

2026-11-26 時点の設計の記録である。判断とその理由は
[ADR-0007](../adr/0007-serialize-token-renewal-across-processes.ja.md) にある。この文書は、
要求、部品ごとの約束と手順、テストの判定基準、作業の順序を定める。リリース後は更新しない。

## 1. 要求

利用者からの改善提案（同じサーバの bridge が何本も同時に動くと、使い捨ての refresh token を発行する
サーバで保存済みのログインが失われる）を、コードと手元の環境で確認のうえ次の要求にした。

| # | 要求 |
|---|------|
| R1 | 同じ `tokens.json` を共有する bridge が何本あっても、期限切れのあとに更新の通信をするのは 1 本だけで、残りはその結果を使う |
| R2 | 使い捨ての refresh token を発行し、使用済みのトークンが再提示されたら grant ごと無効にするサーバでも、R1 の状況で保存済みのログインが失われない。同じ refresh token を 2 回送らない |
| R3 | サーバに 401 で拒否されたアクセストークンが、ファイルに残っていても、更新に失敗したあとでも、再び使われない |
| R4 | `mcp-bridge login` をやり直したら、動いている bridge は MCP クライアントの再起動なしに、次の更新で新しいログインを使う |
| R5 | `mcp-bridge logout` で消したログインを、動いている bridge が書き戻さない |
| R6 | ロックが使えない環境（読み取り専用の state ディレクトリ、ファイルロックの無い OS）でも、更新はこれまでどおり行われ、そのことが stderr に出る。保存に失敗した更新のあとも、1 本だけなら続けて更新できる（v0.3.0 と同じ） |
| R7 | ほかのプロセスがロックを持ったままでも、MCP クライアントへの応答は際限なく止まらない |
| R8 | 更新したこと、ほかの bridge の更新結果を使ったことが stderr に 1 行ずつ出る。更新のときは refresh token が置き換わったかどうかも出る。トークンの値は出さない |
| R9 | 外部依存ゼロ、設定キーの追加なし、stdout は JSON-RPC だけ、refresh token の無いトークンの扱い（ADR-0003）は変えない |
| R10 | 今ビルドできるすべての GOOS でビルドが通る。Linux と macOS ではテストが通る |

### 範囲外

- refresh token を生かし続ける手段（提案書の P3）。ADR-0007「範囲外」。
- サーバ側でトークンを取り消すこと（`logout` はこれまでどおりファイルを消すだけ）。
- `discovery.json` の書き換えの排他。書くのは `login` だけで、`run` は読むだけである。
- ネットワークファイルシステム上の state ディレクトリでロックを効かせること。README に注意を書くだけにする。
- `tokenCommand` の経路（`internal/tokencmd`）。ファイルを共有しない。
- `inspect` の読み込みをロックの中に入れること。`inspect` は `run` と同じ `oauthProvider` を通るので、
  3.2 の最初の読み込みのロックがそのまま効く。それ以外の読み手は無い。
- 更新の応答に `expires_in` が無いとき期限を 0 のまま持つ既存の挙動。401 を受けて更新に入るので、
  更新が止まるわけではない（ADR-0003 と同じく、サーバが判定する）。

## 2. 部品と流れ

```
run / inspect ─ NewProvider ─ tokenLock → tokens.json を読む → 解放
                transport ─ Provider.Token()
                    │ メモリ上のトークンで足りる → そのまま返す（ロックもファイルも触らない）
                    │ 足りない（期限切れ・拒否済み）
                    ▼
                  tokenLock（上限 45 秒）
                    │ 開けない → 警告してロックなしで続ける
                    │ 上限を過ぎた → この要求をエラーにする（refresh token は送らない）
                    ▼
                  tokens.json を読み直す → 判断（表 3.2）→ 必要なら更新の通信 → 保存 → 解放

login  ─ ブラウザでの操作（ロックなし）─ tokenLock → SaveTokens → 解放（上限後は警告してロックなし）
logout ─ oauth.DeleteLogin ─ tokenLock → DeleteTokens → 解放（上限後はエラー）
```

| 部品 | 約束 | 約束しないこと |
|------|------|---------------|
| `lockTokens`（新規、非公開。`internal/oauth/lock_flock.go`・`lock_windows.go`・`lock_other.go`） | `<tokens>.lock` に排他ロックを掛け、解放の関数を返す。開けない・ロックの仕組みが無いときと、上限時間を過ぎたときを、区別できるエラーで返す | ネットワークファイルシステムでの排他。ロックファイルの削除 |
| `NewProvider`（変更） | 最初の読み込みをロックの中で行う | — |
| `Provider.Token()`（変更） | メモリ上のトークンで足りなければ、ロックの中でファイルを読み直して表 3.2 で決める | プロセスをまたいだ `Invalidate` の伝達（拒否は各プロセスが自分で受けて覚える） |
| `oauth.Login`（変更） | 得たトークンの保存をロックの中で行う | ブラウザでの操作の間の排他 |
| `oauth.DeleteLogin`（新規、公開） | ロックの中で `DeleteTokens` する。ディレクトリが無ければ何もせず成功する。`cli.Logout` はこれを呼ぶ | 動いている bridge のメモリ上のアクセストークンを無効にすること |

## 3. 詳細設計

### 3.1 ロック

- パスは `<TokensPath>.lock`。`os.OpenFile(path, O_CREATE|O_RDWR, 0o600)` で開く。開けなければ
  「使えない」エラー（`errLockUnavailable` を包む）を返す。
- `lock_flock.go`（`//go:build darwin || linux || freebsd || netbsd || openbsd || dragonfly`）:
  `syscall.Flock(fd, LOCK_EX|LOCK_NB)` を、取れるか上限時間を過ぎるまで 50 ミリ秒ごとに試す。
  `EWOULDBLOCK`（`EAGAIN`）と `EINTR` なら繰り返す。それ以外のエラーは「使えない」エラーにする。
- `lock_windows.go`: `kernel32` の `LockFileEx` を `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`
  で同じく繰り返し試す。`ERROR_LOCK_VIOLATION` なら繰り返し、それ以外は「使えない」エラー。
  解放は `UnlockFileEx`。標準ライブラリの `syscall` だけで呼ぶ。
- `lock_other.go`（上の 2 つ以外の GOOS。aix・solaris・illumos・plan9・js・wasip1 など）:
  常に「使えない」エラーを返す。今ビルドできる GOOS がビルドできなくならないようにする。
- 上限時間を過ぎたら「待ちきれない」エラー（`errLockTimeout` を包む）を返す。
- 解放はロックを外してからファイルを閉じる。プロセスが落ちればカーネルが解放する。
- 上限時間は 45 秒（定数 `lockWait`）。テストでは呼び出し側の非公開のフィールド
  （`ProviderConfig.lockWait`、`LoginConfig.lockWait`、`deleteLogin` の引数）で短くする。設定キーにはしない（R9）。
- 同じプロセスの中の複数の `Provider` も、別々にファイルを開くので互いに排他される
  （flock は開いたファイルごと、`LockFileEx` はハンドルごと）。テストはこの性質を使う。

### 3.2 `Provider` の判断

**最初の読み込み。** `NewProvider` はロックを取ってから `LoadTokens` する。使えなければロックなしで読む。
待ちきれなければ、ほかのプロセスが更新中である旨のエラーを返す。

**ロックの外**（プロセス内の `sync.Mutex` は今までどおり全体を守る）:

1. 拒否済みでなく refresh token が無い → 保存されたアクセストークンをそのまま返す（ADR-0003、変更なし）。
2. 拒否済みでなく、refresh token があり、アクセストークンが空でなく、`refreshMargin` を含めて期限内 → そのまま返す。
3. それ以外 → 次のロックの中の判断へ進む。

**ロックを取る。** 使えなければ、警告を stderr に 1 行出してロックなしで続ける（R6）。待ちきれなければ、
`another mcp-bridge process is renewing the token for %q; try again` の形のエラーを返す（R7）。
refresh token は送らない。

**ファイルを読み直し**、上から順に最初に当てはまる行で決める。

| # | 状態 | 結果 |
|---|------|------|
| a | ファイルが無い | エラー: ログインが無い（ログアウトされた）。`mcp-bridge login <server>` を案内 |
| b | 読めない・JSON として壊れている | エラー: 読めなかった理由。`mcp-bridge login <server>` を案内 |
| c | このプロセスの直前の更新が保存に失敗しており（`unsavedFrom` が空でない）、ファイルの refresh token がそのとき置き換えられなかったもの（`unsavedFrom`）と同じ | ファイルではなくメモリ上の refresh token で更新する（d と同じ手順）。メモリの方が新しい |
| d | アクセストークンが空でなく、このプロセスが拒否されたもの（`rejectedAccess`）と違い、かつ（refresh token が無い、または `refreshMargin` を含めて期限内） | 採用する。メモリ上のトークンをファイルの内容に置き換え、拒否の記録と `unsavedFrom` を消す。メモリ上と違うアクセストークンを採用したときだけ、「採用した」1 行を出す |
| e | refresh token がある | ファイル上の refresh token で更新する |
| f | それ以外 | エラー: サーバに拒否され、更新する refresh token が無い。`mcp-bridge login <server>` を案内（既存の文言） |

c 以外の行に進んだ時点で `unsavedFrom` は消す（ファイルが書き換えられ、ファイルの方が新しい）。

**更新（c・e）の手順。**

- 送る refresh token を `sent` とする。成功したら、応答に refresh token が無ければ `sent` を引き継ぐ（変更なし）。
- 保存する。成功したら `unsavedFrom` を消す。失敗したら今までどおり警告し、`unsavedFrom` に
  「ファイルに残っている refresh token」を記録する（c なら今の `unsavedFrom` のまま、e なら `sent`）。
- 「更新した」1 行を出し、得たトークンを返す。
- 失敗したときは、今までどおり `refreshing the token for %q failed (run "mcp-bridge login %s" ...)` を返す。
  メモリ上のトークンは、refresh token をファイルの値（c ならメモリの値のまま）にし、アクセストークンを空、
  期限を 0 にする。次の呼び出しは必ずロックの中の判断に入るので、拒否されたトークンを使わず（R3）、
  その間にログインし直されていれば拾える（R4）。

`rejectedAccess` は `Invalidate` の時点のアクセストークンである。`Invalidate` は今までどおり
メモリ上のアクセストークンと期限を消し、`rejected` を立てる。

### 3.3 記録（R8）

`p.logf`（stderr、`mcp-bridge: ` 前置き）に次の形で出す。

```
mcp-bridge: renewed the token for "atlassian" (expires 2026-11-26T20:23:02+09:00; renews automatically; the server issued a new refresh token)
mcp-bridge: renewed the token for "m365-mail" (expires ...; renews automatically; the refresh token was kept)
mcp-bridge: using the token another mcp-bridge process stored for "atlassian" (expires ...; renews automatically)
mcp-bridge: warning: cannot lock the token file for "atlassian", so renewals are not coordinated with other mcp-bridge processes: <理由>
```

- 括弧の中の期限の部分は `Tokens.Describe()` を使う。
- 「置き換わった」は、応答に refresh token があり、`sent` と違う場合。同じ値が返った場合と省略された場合は「kept」。
- 読み取り専用のディレクトリでは、ロックの警告と、既存の保存の警告（`could not be saved`）の 2 行が出る。

### 3.4 `login` と `logout`

- `oauth.Login` は、トークンの交換に成功したあと、ロックを取って `SaveTokens` し、解放する。
  ロックはブラウザでの操作の前には取らない（最大 5 分の待ちのあいだ `run` を止めないため）。
  使えないときと待ちきれないときは、その旨を 1 行 `cfg.Out` に出して、ロックなしで保存する。
- `oauth.DeleteLogin(path)` は、`path` のディレクトリが無ければ何もせず成功する（ログインしたことの
  無いサーバ。今の「nothing to do」の出力をそのまま保つ）。あればロックを取って `DeleteTokens` し、解放する。
  使えなければ、警告を返り値で返してロックなしで削除する。待ちきれなければ削除せずにエラーを返す。
  `tokens.json.lock` は消さない。
- `cli.Logout` は `oauth.DeleteLogin` を呼び、警告があれば `opts.Out` に 1 行出す。
- `refresh()` の「The caller holds the lock」というコメントを、プロセス内の `p.mu` と
  ファイルロックの両方を指す書き方に直す（提案書 5.1 の未決事項）。

## 4. テスト設計

すべて `go test -race` で通す。並行の行は `-count=20` でも通ることを確かめる。

| 対象 | 確かめること | 期待値を決めるもの |
|------|-------------|-------------------|
| ロック | 1 つ目が持っている間、2 つ目は上限時間で「待ちきれない」になる。解放後は取れる。ロックファイルのモードが 0600。開けないディレクトリでは「使えない」になる | 3.1 |
| 読み直し（提案書テスト 1 の反転） | 期限切れのあと A、B の順に `Token()`。B は更新の通信をせず A の結果を返す。テスト用サーバへの更新は 1 回 | 表 3.2 d |
| reuse detection（提案書テスト 2 の反転） | 同じ流れを reuse detection ありのサーバで行い、そのあと新しく作った `Provider` C も成功する | R2 |
| 同時に 6 本 | 6 つの `Provider` が同時に `Token()`。テスト用サーバは最初の更新の応答を、ほかの 5 本が `Token()` に入ってから 200 ミリ秒止める。全部成功し、更新の通信は 1 回、同じ refresh token が 2 回届かない。次の期限切れのあとも成功する | R1、R2 |
| 本物の別プロセス | テストバイナリを子プロセスとして 6 本起動し、親が立てたテスト用サーバ（上と同じく最初の応答を止める）に同時に更新させる。全部成功し、更新の通信は 1 回 | R1（同じプロセス内の検証の補強） |
| テストがロックを見ていること | 実装の段で一度だけ、ロックを何もしないものに差し替えて「同時に 6 本」と「本物の別プロセス」が落ちることを確かめ、結果を作業記録に残す（差し替えはコミットしない） | テストが判定できることの確認 |
| 拒否されたトークン | A と B が `at-0` を持ち、A が 401 を受けて更新する。ファイルに `at-0` が残っている状態で A が再び `at-0` を採用しない。B が 401 を受けたら A の更新結果を採用する | R3、表 3.2 d |
| 拒否のあとの更新の失敗 | 401 のあとの更新が失敗したら、次の `Token()` は `at-0` を返さず、再びロックの中で判断する | R3、3.2 の失敗時の手順 |
| 保存に失敗した更新のあと | 読み取り専用のディレクトリで 1 本の `Provider` が 2 回続けて期限切れを迎える。使い捨ての refresh token を発行し reuse detection のあるサーバで、2 回とも成功し、使用済みの refresh token を送らない | R6、表 3.2 c |
| 保存の失敗のあとにファイルが変わった | 保存に失敗したあと、ファイルを新しいログインに書き換えると、次の更新はファイルの方を使う | 表 3.2 c の条件 |
| ログインし直し | B が `invalid_grant` で失敗したあと、ファイルを新しいログインに書き換えると、B の次の `Token()` が成功する。refresh token の無い新しいログインでも成功する | R4、表 3.2 d・e |
| ログアウト | 期限切れの状態でファイルを消すと、`Token()` はログインを案内するエラーを返し、ファイルを作り直さない | R5、表 3.2 a |
| 壊れたファイル | 期限切れの状態でファイルを壊すと、エラーにログインの案内が入る | 表 3.2 b |
| ロックが使えない | 読み取り専用のディレクトリ（既存テスト、変更なしで通る）。更新が成功し、ロックの警告と保存の警告が出る | R6 |
| 待ちきれない | 別のロックが持たれたまま上限時間を過ぎると、`Token()` は「更新中」のエラーを返し、テスト用サーバに更新が届かない | R7、R2 |
| 最初の読み込み | 別のロックが持たれている間、`NewProvider` は待つ。上限を過ぎればエラー | 3.2 |
| 記録 | 更新・採用の行が出る。置き換わった場合と保たれた場合の文言。どの行にもアクセストークンと refresh token の値が入らない | R8、3.3 |
| `login` の保存 | 別のロックが持たれている間は保存が待ち、解放後に保存される。上限を過ぎたら警告してロックなしで保存する | 3.4 |
| `logout` | 別のロックが持たれている間は削除が待つ。上限を過ぎたら削除せずにエラー。ロックファイルが残る。ディレクトリが無ければ警告もエラーも出ない | 3.4 |
| 既存の挙動 | 既存のテストが変更なしで通る（ADR-0003 の経路を含む） | R9 |
| ビルド | `GOOS` を darwin・linux・windows・freebsd・openbsd・netbsd・dragonfly・solaris・aix・illumos で `go vet` が通る。`make test-linux` が通る | R10 |

**テスト用サーバ。** 提案書の付録 A にある、使い捨ての refresh token を発行し、reuse detection の有無を
切り替えられるトークンエンドポイントを書き直して使う。届いた refresh token を順に記録し、同じものが
2 回届いたかを調べられるようにする。最初の応答を止める仕掛けを足す。

**本物の別プロセスのテスト。** `os.Args[0]` を環境変数つきで再実行する。子は `TestMain` で
`Provider` を作り、「開始」ファイルが置かれるのを待ってから `Token()` を 1 回呼び、結果を stdout に書いて終わる。
親は 6 本を起動してから「開始」ファイルを置き、全員の終了を待つ。

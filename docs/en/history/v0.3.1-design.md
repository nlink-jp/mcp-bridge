# v0.3.1 design note: renewing tokens one at a time across concurrent bridges

A record of the design as of 2026-11-26. The decisions and their reasons are in
[ADR-0007](../adr/0007-serialize-token-renewal-across-processes.md). This note
fixes the requirements, each component's contract and procedure, what decides a
test's expected result, and the order of work. It is not updated after the
release.

## 1. Requirements

A user's improvement proposal (when several bridges for the same server run at
once, a server that issues single-use refresh tokens loses the stored login)
was checked against the code and the maintainer's machine and turned into these
requirements.

| # | Requirement |
|---|-------------|
| R1 | However many bridges share one `tokens.json`, only one of them sends a renewal request after an expiry, and the rest use its result |
| R2 | With a server that issues single-use refresh tokens and revokes the whole grant when a spent one is presented again, the stored login survives the situation in R1. The same refresh token is never sent twice |
| R3 | An access token the server rejected with 401 is not used again, neither while it is still in the file nor after a failed renewal |
| R4 | After `mcp-bridge login` is run again, a running bridge uses the new login at its next renewal, without restarting the MCP client |
| R5 | A login deleted with `mcp-bridge logout` is not written back by a running bridge |
| R6 | Where the lock cannot be used (a read-only state directory, an OS with no file locking), renewal works as before and stderr says so. After a renewal that could not be saved, a single bridge can still renew again (as in v0.3.0) |
| R7 | Even while another process holds the lock, the answer to the MCP client is not held back without limit |
| R8 | One line on stderr for a renewal and one for adopting another bridge's renewal. A renewal also says whether the refresh token was replaced. No token value is printed |
| R9 | Zero external dependencies, no new configuration key, stdout carries only JSON-RPC, and the handling of tokens without a refresh token (ADR-0003) does not change |
| R10 | Every GOOS that builds today still builds. Tests pass on Linux and macOS |

### Out of scope

- Keeping the refresh token alive (the proposal's P3). ADR-0007, "Out of scope".
- Revoking tokens on the server (`logout` still only deletes the file).
- Exclusion for writes to `discovery.json`. Only `login` writes it; `run` only reads it.
- Making the lock work on a state directory on a network file system. The README carries a note, nothing more.
- The `tokenCommand` route (`internal/tokencmd`). It shares no file.
- Putting `inspect`'s read under the lock. `inspect` goes through the same
  `oauthProvider` as `run`, so the lock on the first read in 3.2 already covers
  it. There is no other reader.
- The existing behaviour of keeping a zero expiry when a renewal response has no
  `expires_in`. The 401 that follows starts a renewal, so renewal does not stop
  (as in ADR-0003, the server is the judge).

## 2. Components and flow

```
run / inspect ─ NewProvider ─ tokenLock → read tokens.json → release
                transport ─ Provider.Token()
                    │ the token in memory will do → return it (no lock, no file)
                    │ it will not (expired, rejected)
                    ▼
                  tokenLock (limit 45 s)
                    │ cannot be opened → warn and continue without the lock
                    │ limit passed → fail this request (no refresh token is sent)
                    ▼
                  read tokens.json again → decide (table 3.2) → renew if needed → save → release

login  ─ browser (no lock) ─ tokenLock → SaveTokens → release (after the limit: warn, no lock)
logout ─ oauth.DeleteLogin ─ tokenLock → DeleteTokens → release (after the limit: error)
```

| Component | Contract | Not promised |
|-----------|----------|--------------|
| `lockTokens` (new, unexported; `internal/oauth/lock_flock.go`, `lock_windows.go`, `lock_other.go`) | Takes an exclusive lock on `<tokens>.lock` and returns a function that releases it. Returns distinguishable errors for "cannot be opened / no locking on this OS" and for "limit passed" | Exclusion on a network file system. Deleting the lock file |
| `NewProvider` (changed) | Does its first read under the lock | — |
| `Provider.Token()` (changed) | When the token in memory will not do, reads the file again under the lock and decides by table 3.2 | Passing an `Invalidate` between processes (each process receives and remembers its own rejection) |
| `oauth.Login` (changed) | Saves the obtained tokens under the lock | Exclusion while the browser is open |
| `oauth.DeleteLogin` (new, exported) | Runs `DeleteTokens` under the lock. Succeeds doing nothing when the directory does not exist. `cli.Logout` calls it | Invalidating the access token in a running bridge's memory |

## 3. Detailed design

### 3.1 The lock

- The path is `<TokensPath>.lock`, opened with
  `os.OpenFile(path, O_CREATE|O_RDWR, 0o600)`. If it cannot be opened, an
  "unusable" error (wrapping `errLockUnavailable`) is returned.
- `lock_flock.go` (`//go:build darwin || linux || freebsd || netbsd || openbsd || dragonfly`):
  tries `syscall.Flock(fd, LOCK_EX|LOCK_NB)` every 50 milliseconds until it
  succeeds or the limit passes. `EWOULDBLOCK` (`EAGAIN`) and `EINTR` are
  retried; any other error becomes an "unusable" error.
- `lock_windows.go`: tries `kernel32`'s `LockFileEx` with
  `LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY` in the same way.
  `ERROR_LOCK_VIOLATION` is retried; anything else is an "unusable" error.
  Released with `UnlockFileEx`. Called through the standard library's `syscall`
  only.
- `lock_other.go` (every other GOOS: aix, solaris, illumos, plan9, js, wasip1
  and so on): always returns an "unusable" error, so that no GOOS that builds
  today stops building.
- When the limit passes, a "limit passed" error (wrapping `errLockTimeout`) is
  returned.
- Release unlocks first, then closes the file. If the process dies, the kernel
  releases the lock.
- The limit is 45 seconds (constant `lockWait`). Tests shorten it through
  unexported fields on the callers (`ProviderConfig.lockWait`,
  `LoginConfig.lockWait`, an argument of `deleteLogin`). It is not a
  configuration key (R9).
- Several `Provider`s in one process exclude each other too, because each opens
  the file separately (flock is per open file, `LockFileEx` per handle). The
  tests rely on this.

### 3.2 How `Provider` decides

**The first read.** `NewProvider` takes the lock and then runs `LoadTokens`. If
the lock is unusable, it reads without it. If the limit passes, it returns an
error saying another process is renewing.

**Outside the lock** (the in-process `sync.Mutex` still guards the whole call):

1. Not rejected and no refresh token → return the stored access token as is
   (ADR-0003, unchanged).
2. Not rejected, a refresh token present, the access token not empty and within
   its expiry including `refreshMargin` → return it as is.
3. Anything else → go on to the decision under the lock.

**Take the lock.** If it is unusable, print one warning line on stderr and
continue without it (R6). If the limit passes, return an error of the form
`another mcp-bridge process is renewing the token for %q; try again` (R7). No
refresh token is sent.

**Read the file again** and decide by the first row that applies.

| # | State | Result |
|---|-------|--------|
| a | The file does not exist | Error: no login (it was logged out). Names `mcp-bridge login <server>` |
| b | Unreadable, or not valid JSON | Error: why it could not be read. Names `mcp-bridge login <server>` |
| c | This process's last renewal could not be saved (`unsavedFrom` not empty), and the file's refresh token is the one that renewal failed to replace (`unsavedFrom`) | Renew with the refresh token in memory, not the file's (same procedure as e). Memory is newer |
| d | The access token is not empty, differs from the one rejected for this process (`rejectedAccess`), and (there is no refresh token, or it is within its expiry including `refreshMargin`) | Adopt it. Replace the tokens in memory with the file's, and clear the rejection and `unsavedFrom`. Print the "adopted" line only when the adopted access token differs from the one in memory |
| e | There is a refresh token | Renew with the refresh token in the file |
| f | Anything else | Error: the server rejected the login and there is no refresh token to renew it. Names `mcp-bridge login <server>` (the existing wording) |

Reaching any row other than c clears `unsavedFrom` (the file was rewritten, so
the file is newer).

**The renewal procedure (c and e).**

- Call the refresh token sent `sent`. On success, if the response has no
  refresh token, `sent` is kept (unchanged).
- Save. On success, clear `unsavedFrom`. On failure, warn as before and record
  in `unsavedFrom` the refresh token left in the file (for c, the current
  `unsavedFrom` stays; for e, `sent`).
- Print the "renewed" line and return the obtained token.
- On failure, return the existing
  `refreshing the token for %q failed (run "mcp-bridge login %s" ...)`. The
  tokens in memory get the file's refresh token (for c, the in-memory one stays),
  an empty access token and a zero expiry. The next call therefore always goes
  through the decision under the lock: the rejected token is not used (R3), and
  a login made in the meantime is picked up (R4).

`rejectedAccess` is the access token at the moment of `Invalidate`.
`Invalidate` still clears the in-memory access token and expiry and sets
`rejected`.

### 3.3 Records (R8)

Printed through `p.logf` (stderr, prefixed `mcp-bridge: `) in these forms.

```
mcp-bridge: renewed the token for "atlassian" (expires 2026-11-26T20:23:02+09:00; renews automatically; the server issued a new refresh token)
mcp-bridge: renewed the token for "m365-mail" (expires ...; renews automatically; the refresh token was kept)
mcp-bridge: using the token another mcp-bridge process stored for "atlassian" (expires ...; renews automatically)
mcp-bridge: warning: cannot lock the token file for "atlassian", so renewals are not coordinated with other mcp-bridge processes: <reason>
```

- The expiry part in parentheses comes from `Tokens.Describe()`.
- "Replaced" means the response carried a refresh token different from `sent`.
  The same value returned, or none, is "kept".
- In a read-only directory two lines appear: the lock warning and the existing
  save warning (`could not be saved`).

### 3.4 `login` and `logout`

- `oauth.Login`, after the token exchange succeeds, takes the lock, runs
  `SaveTokens` and releases it. It does not take the lock before the browser
  step (so `run` is not held for the up to five minutes that step may take).
  When the lock is unusable or the limit passes, one line on `cfg.Out` says so
  and the tokens are saved without the lock.
- `oauth.DeleteLogin(path)` succeeds doing nothing when `path`'s directory does
  not exist (a server never logged in to; the current "nothing to do" output
  stays as it is). Otherwise it takes the lock, runs `DeleteTokens` and releases
  it. When the lock is unusable it returns a warning and deletes without the
  lock. When the limit passes it deletes nothing and returns an error.
  `tokens.json.lock` is not deleted.
- `cli.Logout` calls `oauth.DeleteLogin` and prints any warning as one line on
  `opts.Out`.
- The "The caller holds the lock" comment on `refresh()` is rewritten so that it
  names both the in-process `p.mu` and the file lock (an open point in section
  5.1 of the proposal).

## 4. Test design

Every test passes under `go test -race`. The concurrent rows are also checked
with `-count=20`.

| Subject | What is checked | What decides the expected result |
|---------|-----------------|----------------------------------|
| The lock | While a first lock is held, a second gets "limit passed" at the limit. After release it can be taken. The lock file's mode is 0600. In a directory that cannot be written it is "unusable" | 3.1 |
| Reading again (the proposal's test 1, reversed) | After expiry, `Token()` on A, then on B. B sends no renewal request and returns A's result. The test server sees one renewal | Table 3.2 d |
| Reuse detection (the proposal's test 2, reversed) | The same flow against a server with reuse detection, after which a newly created `Provider` C also succeeds | R2 |
| Six at once | Six `Provider`s call `Token()` together. The test server holds its answer to the first renewal for 200 ms after the other five have entered `Token()`. All succeed, one renewal request, no refresh token received twice. They succeed again after the next expiry | R1, R2 |
| Real separate processes | The test binary is started six times as child processes, renewing together against a test server started by the parent (holding the first answer as above). All succeed, one renewal request | R1 (backs up the in-process check) |
| The tests see the lock | Once, during implementation, the lock is replaced with one that does nothing, and "six at once" and "real separate processes" are confirmed to fail; the result goes into the work record (the replacement is not committed) | Confirms the tests can decide |
| A rejected token | A and B hold `at-0`; A gets a 401 and renews. With `at-0` still in the file, A does not adopt `at-0` again. When B gets a 401, it adopts A's renewal | R3, table 3.2 d |
| A failed renewal after a rejection | If the renewal after a 401 fails, the next `Token()` does not return `at-0` and decides under the lock again | R3, the failure procedure in 3.2 |
| After a renewal that could not be saved | In a read-only directory one `Provider` passes two expiries in a row. Against a server issuing single-use refresh tokens with reuse detection, both succeed and no spent refresh token is sent | R6, table 3.2 c |
| The file changed after a failed save | After a failed save, rewriting the file with a new login makes the next renewal use the file's | The condition of table 3.2 c |
| Logging in again | After B fails with `invalid_grant`, rewriting the file with a new login makes B's next `Token()` succeed. Also with a new login that has no refresh token | R4, table 3.2 d and e |
| Logging out | Deleting the file while the token has expired makes `Token()` return an error naming the login, and the file is not recreated | R5, table 3.2 a |
| A corrupt file | Corrupting the file while the token has expired gives an error naming the login | Table 3.2 b |
| Lock unusable | A read-only directory (the existing test, passing unchanged). The renewal succeeds and both the lock warning and the save warning appear | R6 |
| Limit passed | With another lock held past the limit, `Token()` returns the "renewing" error and no renewal reaches the test server | R7, R2 |
| The first read | While another lock is held, `NewProvider` waits; past the limit, it fails | 3.2 |
| Records | The renewal and adoption lines appear, with the wording for replaced and for kept. No line contains an access token or refresh token value | R8, 3.3 |
| `login`'s save | While another lock is held, the save waits and happens after release. Past the limit, it warns and saves without the lock | 3.4 |
| `logout` | While another lock is held, the deletion waits. Past the limit, nothing is deleted and it fails. The lock file stays. With no directory, no warning and no error | 3.4 |
| Existing behaviour | The existing tests pass unchanged (including the ADR-0003 route) | R9 |
| Builds | `go vet` passes with `GOOS` set to darwin, linux, windows, freebsd, openbsd, netbsd, dragonfly, solaris, aix and illumos. `make test-linux` passes | R10 |

**The test server.** The token endpoint from appendix A of the proposal —
issuing single-use refresh tokens, with reuse detection switchable — rewritten.
It records each refresh token it receives so that a repeat can be detected, and
gains a switch that holds its first answer.

**The real-process test.** `os.Args[0]` is run again with an environment
variable. In the child, `TestMain` builds a `Provider`, waits for a "start"
file to appear, calls `Token()` once, writes the result to stdout and exits.
The parent starts six, then creates the "start" file and waits for all of them.

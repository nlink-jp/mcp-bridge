# v0.3.0 design note: connecting to MCP servers protected by Entra ID

A record of the design as of 2026-11-17. The decisions and their reasons are in
[ADR-0006](../adr/0006-discovery-with-a-pre-registered-client.md). This note
fixes the requirements, each component's contract and procedure, what decides a
test's expected result, and the order of work. It is not updated after the
release.

## 1. Requirements

A user's report (mcp-bridge cannot connect to the Microsoft Agent 365 MCP
servers) was checked and turned into these requirements.

| # | Requirement |
|---|-------------|
| R1 | A login succeeds with a client whose redirect URI is registered as `http://localhost:<port>/callback` |
| R2 | A configuration holding only `clientId` and the listener settings takes the authorization and token endpoints from what the server publishes, and performs no dynamic registration |
| R3 | The authorization server metadata of Entra ID can be fetched |
| R4 | The scopes the MCP server names are the ones requested |
| R5 | Entra ID issues a refresh token |
| R6 | Several servers sharing one `clientId` and one port can be logged in to one after another and `run` at the same time |
| R7 | Because the developers cannot observe the server, the output of `login` that a user pastes is enough to tell what was decided where |
| R8 | Existing configurations (all URLs written, `"oauth": {}`) work without being rewritten |

R6 already holds (`run` does not use the port). Tests pin it so the change does
not break it.

### Out of scope

- A configurable path for the redirect URI (not taken up in ADR-0006).
- Sending the `resource` parameter, checking that the authorization server
  advertises PKCE support, checking the `issuer`, and sending `prompt=consent`
  (ADR-0006, "What is still not done").
- What happens when the configured `url` is rewritten and the server is used
  without logging in again. The stored token goes to the `url` that is written.
  As with static headers and a token command, the person who writes the
  configuration decides the destination.
- The shape of the refresh request. It stays `grant_type` and `refresh_token`
  (and `client_id`). Entra ID's documentation makes `scope` optional there.

## 2. Components and flow

These components change. No new component is added.

| Component | Where | Requirements it carries |
|-----------|-------|-------------------------|
| Configuration validation | `internal/config` | R1, R2, R8 |
| Callback listener | `internal/oauth` (`startCallbackServer`) | R1 |
| Discovery | `internal/oauth` (`discover` and below) | R2, R3, R4, R5, R7, R8 |
| Shared transport settings and output | `internal/oauth` (the HTTP client), `internal/cli` (handing the settings over, what `run` reads) | R2, R6, R7 |

The flow of `login` is below. Bold marks what changes.

1. Read and validate the configuration. **(`callbackHost`, a block without URLs)**
2. Start the callback listener. **(host name, `::1`)**
3. If the configuration has no URLs, discover.
   1. Send an unauthenticated request to the MCP server and read the 401. **(`scope` is read too)**
   2. Fetch the MCP server's metadata. **(two well-known locations, the `resource` check, `scopes_supported`)**
   3. Fetch the authorization server's metadata. **(the third location)**
   4. Decide the client. **(no registration when there is a `clientId`)**
   5. Decide the scopes. **(order, `offline_access`)**
   6. Store and print the result. **(sources, the `url`)**
4. Authorize in the browser, exchange the code for tokens, store them. (unchanged)

`run` reads the token endpoint from the stored result. One thing about that
changes (3.4).

On R8. A configuration with all URLs written does not go through discovery, so
it behaves as it did. `"oauth": {}` does go through discovery, and so takes the
four changes listed in ADR-0006's Consequences.

## 3. Detailed design

### 3.1 Configuration validation

**Input:** the `oauth` block. The one new key is `callbackHost` (a string,
optional).

**Rules:** an empty block (`{}`) is not validated (as before: discover and
register). Otherwise all of the following are checked and every problem is
reported together. New rules are marked ★.

| Condition | Result |
|-----------|--------|
| No `clientId` | Error (as before) |
| ★ Only one of `authorizeUrl` and `tokenUrl` | Error, saying to write both or leave both out |
| ★ Both URLs left out and a `clientSecret` present | Error, saying to write the URLs to use a secret |
| ★ `callbackHost` is none of `""`, `"127.0.0.1"`, `"localhost"` | Error |
| A URL is not `https`, the port is out of range, `callbackScheme` or `clientAuthMethod` has a bad value or combination | Error (as before) |

A block holding only `callbackHost` is not empty (it needs `clientId`). With
the URLs left out and `clientAuthMethod` set to `basic`, the existing rule
(`basic` needs a secret) reports the error.

**Output:** when `callbackHost` is not written, its value is `localhost` if
`callbackScheme` is `https` and `127.0.0.1` otherwise. `callbackScheme:
"https"` with `callbackHost: "127.0.0.1"` is allowed (the certificate covers
both names).

**The mode name shown:** `list` and `inspect` gain no new mode name. A block
with a `clientId` shows as `oauth` whether or not it has URLs.

### 3.2 Callback listener

**Input:** host name, port (0 leaves it to the OS), scheme.

**Procedure:**

1. Listen on `127.0.0.1:<port>`. On failure, end with the existing error.
2. When the host name is `localhost`, also listen on `[::1]` at the port that
   was settled.
   - If that works, both answer the same way.
   - If it does not, try listening on `[::1]:0`. If that fails too, the machine
     has no IPv6 loopback: print nothing and carry on with `127.0.0.1` alone.
     If `[::1]:0` works, the port is in use elsewhere: print this one line and
     carry on — "could not listen on `[::1]:<port>`; if the browser does not
     show mcp-bridge's completion page after you authorize, replace `localhost`
     with `127.0.0.1` in the address bar and load it again". The same step
     reaches the listener whether the browser connected to another process on
     `::1` or failed to connect.
3. When the scheme is `https`, both listeners use TLS with the same certificate
   (the certificate is as before).
4. The redirect URI is `<scheme>://<host>:<port>/callback`.

**Output:** the redirect URI and the place the code is waited for. Every
listener is closed at the end.

### 3.3 Discovery

**Input:** the MCP server's `url`, the redirect URI, the configured `clientId`
(empty means the configuration that registers dynamically), where to store.

**Output:** the authorization endpoint, the token endpoint, a client (only when
one was registered dynamically), and the scopes with their source.

**Reuse:** with a `clientId`, the stored result is not used; discovery runs
every time. Without one, the stored result is reused only when both its `url`
and its redirect URI match this login's and it records a client. An old stored
result that records no `url` is not reused.

**Step 1 — read the 401.** Send an unauthenticated `initialize` (as before). On
a 401, take `resource_metadata` and `scope` out of `WWW-Authenticate`. When the
answer is not a 401, or when there is no `resource_metadata`, go on to the
well-known locations in step 2. When the server gives no answer at all, end
there with an error: the other candidates are on the same host and would only
repeat the failure (changed after the checks against the real thing showed a
server that was merely unreachable being reported as publishing no metadata).

The header is read by its grammar (the scheme and parameter list of RFC 9110
§11.2), not by searching the string. The scheme name and parameter names are
case-insensitive. Values are read both quoted (resolving `\` escapes) and
unquoted. With several header lines, they are taken in order and the first
`Bearer` challenge that has the parameter wins. A line that does not fit the
grammar is skipped, and so is one that gives a challenge the same parameter
twice. A value that is empty or only whitespace counts as absent.

**Step 2 — the MCP server's metadata.** Fetch the candidates in order and take
the first usable one.

1. The `resource_metadata` URL from the 401 (when there is one, only it is tried)
2. `<origin>/.well-known/oauth-protected-resource<the url's path>` (with the
   `url`'s query, if it has one; skipped when the path is just `/`, since it is
   then the same as 3 — RFC 9728 §3.1)
3. `<origin>/.well-known/oauth-protected-resource`

Usable means: it reads as JSON, it lists at least one `authorization_servers`
entry, and its `resource` matches the `url`. A match is the same scheme and
host compared without case, the same port (the scheme's default when none is
written), and a `resource` path that is a leading part of the `url`'s path by
whole segments (a trailing `/` makes no difference; `/mcp` matches `/mcp/x` and
does not match `/mcpx`). Paths are compared as written, so `%2F` is not a
separator. Queries are not compared. A `resource` with user information
(`user@`) does not match.

A document with no `resource` is not used, and the next candidate is tried. A
`resource` that does not match ends the login with an error and no further
candidates are tried. The error shows both values and says that what the server
publishes disagrees with the `url`. The first entry of `authorization_servers`
is the authorization server (as before).

**Step 3 — the authorization server's metadata.** For an issuer with a path,
try in this order.

1. `<origin>/.well-known/oauth-authorization-server<path>`
2. `<origin>/.well-known/openid-configuration<path>`
3. `<issuer>/.well-known/openid-configuration` (new)

Without a path, only 1 and 2. Usable means both the authorization and token
endpoints are present (as before).

**When steps 2 and 3 fail.** As before, step 3 is tried with the `url`'s own
host as the issuer. When everything fails, the error lists the places tried and
what each returned (as before). The remedy the error names depends on the
configuration: with a `clientId`, "write `authorizeUrl` and `tokenUrl`";
without one, the existing wording.

**The condition on URLs.** A discovered URL (a metadata URL, the issuer, the
authorization, token and registration endpoints) is used only when it is
`https`. Only when the configured `url` is `http` are `http` URLs used too. A
URL that fails the condition makes its candidate a failure, and the reason goes
into the list of attempts.

**Step 4 — the client.** With a `clientId`, nothing is registered. Without one,
register as before, and end with the existing error when there is no
registration endpoint.

**Step 5 — the scopes.** Discovery returns the first of these that exists.

1. The 401's `scope`
2. `scopes_supported` in the MCP server's metadata
3. `scopes_supported` in the authorization server's metadata
4. None

When 1 or 2 decided it, the authorization server's `scopes_supported` holds
`offline_access`, and the decided scopes do not, it is appended. When the
configuration has `scopes`, the configured value is used and not discovery's
(the existing overlay rule).

**Step 6 — store and print.** The result is stored with the `url` added. Only
when discovery ran, `login` prints:

- the authorization server (the issuer) and the metadata URL that named it
- what happened with the client (the configured one is used / one was registered)
- the scopes requested and their source (the configuration / the server's 401 /
  the server's metadata / the authorization server's metadata / none), and
  that `offline_access` was added when it was

When an earlier registration is reused, discovery did not run, so the existing
line (saying it is reused) is joined by the scopes, shown as "from the stored
registration". Tokens, secrets and authorization codes are not printed (as
before).

**Bounds.** A metadata document is read up to 1 MiB and a request takes at most
30 seconds (as before). Discovery makes at most one 401 probe, two requests for
the MCP server's metadata, three for the authorization server's metadata, two
on the existing fallback route, and one registration.

### 3.4 Shared transport settings, output, and what `run` reads

**Redirects.** The HTTP client used for the login and for refreshing does not
follow a redirect from an `https` URL to anything but `https`; it returns an
error. A request that began as `http` (when the configured `url` is `http`) is
held to the same once it has reached `https`, and otherwise follows Go's
default. The limit on the number of redirects is Go's default (10). A redirect
that was not followed counts as an answer from the server, so step 1 goes on
to the well-known locations.

**Sanitising the output.** What `login` prints, and the errors discovery and
the login return, carry text the server returned (the issuer, scopes, URLs,
error descriptions). At the one place just before it is written to the
terminal, control characters other than newline and tab, and the
bidirectional control characters, are removed. This
covers all of `login`'s output and the error a command prints last. `inspect`'s
output and `run`'s log print what a server returned too, so they go through
the same place. The JSON-RPC messages `run` relays are not touched.

**Handing the settings over.** `callbackHost` is passed from the configuration
to the login.

**What `run` reads.** The stored token endpoint is held to the same condition
on URLs as discovery applies. An earlier version stored it unchecked, so one
that fails the condition is not used, and the session ends naming the login
to run. The client secret is taken from the stored result only when the
client ID was taken from it too. This keeps a secret from an earlier
dynamic registration from being sent paired with a configured `clientId`, when
`"oauth": {}` was rewritten to a `clientId`-only block and the server was not
logged in to again.

## 4. Test design

What decides the expected result is fixed per test.

| Subject | What is checked | What decides the expected result |
|---------|-----------------|----------------------------------|
| Configuration validation | Each row of the table in 3.1, and that the existing examples still pass | The table in 3.1 |
| Listener | The redirect URI for the four combinations of host name and scheme. With `localhost`, an answer on both `127.0.0.1` and `::1`. With the `::1` port taken, one line printed and the login continuing | The procedure in 3.2 |
| Reading the 401 | Extracting `scope` and `resource_metadata`: quoted and unquoted, name case, several lines, an empty value, not picking up text inside `error_description`, lines that do not fit the grammar (table test) | The grammar of RFC 9110 §11.2 and RFC 6750 §3 |
| Metadata candidates | The two locations when the 401 names no URL and when the answer is not a 401, a `url` with a query, `resource` matching, not matching and missing (the comparison as a table test: default port, case, trailing `/`, no match across a segment boundary) | 3.3 step 2, RFC 9728 §3.1 |
| Authorization server location | Metadata is fetched from an issuer whose document exists only at the third location | Entra ID as measured (2026-11-17: 1 and 2 return 404, 3 returns 200) |
| Scopes | The four steps and the conditions for `offline_access` (table test of a pure function) | 3.3 step 5 |
| The condition on URLs | With an `https` `url`, an `http` destination is not used; with an `http` `url`, it is | 3.3 "The condition on URLs" |
| Redirects | A redirect from `https` to `http` is not followed (fetching metadata and the token request) | 3.4 |
| Sanitising the output | Control characters in text the server returned do not appear in `login`'s output or its errors | 3.4 |
| Configuration wins | With `scopes` configured, exactly those are requested and `offline_access` is not added | 3.3 step 5 |
| Handing the settings over | The configured `callbackHost` reaches the login | 3.4 |
| The Entra-shaped end to end | A login against the stand-in server below with a `clientId`-only block: the query of the authorization URL (`client_id`, `scope`, `redirect_uri`), zero registration requests, no `client_secret` in the token request, the content of the stored result | All of 3.3, and the values measured from Entra ID's public metadata |
| Reuse | With a `clientId`, a second login discovers again. Without one, a stored result for another `url` and an old stored result are not reused | 3.3 "Reuse" |
| The `run` route | A refresh request goes to the stored token endpoint with the configured `clientId`. A secret left in the stored result by an earlier dynamic registration is not sent | The flow in section 2, 3.4 |
| Several servers (R6) | Two servers with the same `clientId` and port can be logged in to in turn and their stored results stay separate. The `run` route does not use the port | R6 |
| Messages | An error for a block with a `clientId` gives no "dynamic registration" advice; no token appears in the output | 3.3 steps 2 and 6 |
| Compatibility | The existing tests pass unchanged except one. The validation test expecting "a block with only `clientId` is an error" is reversed by this design | R8 |

**The Entra-shaped stand-in server.** It is started inside the test. The MCP
server answers 401 with `resource_metadata`. The metadata returns `resource`,
an issuer with a path, and API scopes. The authorization server's document is
served only at the third location; the others return 404. Its content follows
Entra ID's public metadata (no registration endpoint, `scopes_supported` of
`openid profile email offline_access`, no `none` in the list of authentication
methods, no `code_challenge_methods_supported`).

**Checks against the real thing (before the release, by hand).** There is no
Entra ID tenant, but these can be checked against real services.

1. Fetching the real Entra ID metadata and building the authorization URL. A
   stand-in MCP server started locally names
   `https://login.microsoftonline.com/common/v2.0` as its authorization server,
   and `login` runs with a made-up `clientId`. If the browser reaches Entra
   ID's page and the error is that the client is not found, everything up to
   that point is right.
2. Discovery against a real MCP server. `login` with a `clientId`-only block
   against GitHub's MCP server (which publishes metadata and has no
   registration endpoint), reading the discovery output against what GitHub
   publishes.
3. Failure messages. Cause a `resource` mismatch, missing metadata and a port
   collision, and read the terminal output.
4. Log in with the `::1` port held by another process, and see which side the
   browser connects to and that the step in 3.2's one line does reach the
   listener.

## 6. The run against a tenant (after the release)

On 2026-11-17 the reporting user ran v0.3.0 against a Microsoft Agent 365
server (`mcp_MailTools`) in their tenant and sent back the output and their own
measurements, with the tenant ID and the client ID replaced. The `oauth` block
held `clientId`, `"clientAuthMethod": "none"`, `"callbackHost": "localhost"`
and `"callbackPort": 8080`, and nothing else.

**What worked.** The first login. `inspect`, which listed 22 tools from
`Microsoft.MCPPlatform.WebApi 0.1.3604.4207` (protocol `2025-06-18`) and
reported `oauth (credential accepted)`. Renewal with the refresh token.

**What the server answers to an unauthenticated request** — the response
section 4 could not check.

- `initialize` without a token: `401` with an empty body and
  `WWW-Authenticate: Bearer resource_metadata="https://agent365.svc.cloud.microsoft/.well-known/oauth-protected-resource/agents/tenants/<tenant-id>/servers/mcp_MailTools"`. There is no `scope`
  parameter.
- `/.well-known/oauth-protected-resource` at the root of the host:
  `400 EndpointInvalid`.
- The document the challenge names (`200`):

```json
{
  "resource_name": "mcp_MailTools",
  "resource": "https://agent365.svc.cloud.microsoft/agents/tenants/<tenant-id>/servers/mcp_MailTools",
  "authorization_servers": ["https://login.microsoftonline.com/organizations/v2.0"],
  "scopes_supported": [
    "https://agent365.svc.cloud.microsoft/agents/tenants/<tenant-id>/servers/mcp_MailTools/.default",
    "openid",
    "profile",
    "offline_access"
  ],
  "bearer_methods_supported": ["header"]
}
```

**The login's output.**

```text
Discovering the authorization server...
Authorization server: https://login.microsoftonline.com/organizations/v2.0 (named by https://agent365.svc.cloud.microsoft/.well-known/oauth-protected-resource/agents/tenants/<tenant-id>/servers/mcp_MailTools)
Client: <client-id> (the pre-registered one from the configuration)
Scopes: https://agent365.svc.cloud.microsoft/agents/tenants/<tenant-id>/servers/mcp_MailTools/.default openid profile offline_access (from the server's metadata)
Opening a browser to authorize m365-mail.
...
Waiting for the authorization callback...
Exchanging the authorization code for tokens...
Logged in to m365-mail. expires <time>; renews automatically
```

**Renewal.** With `expires_at` in `tokens.json` rewritten to a past time,
`inspect` sent a refresh request without `scope`. Entra ID returned a new
access token and a new refresh token, both were stored, and the server accepted
the new token.

**Read against the design.**

| Design | Observed |
|--------|----------|
| 3.3 step 1: read the 401 and follow `resource_metadata` | The challenge named the metadata, so no well-known location was guessed. The root location would have answered 400 |
| 3.3 `resource` check, by leading path | `resource` equals the `url` exactly. Exact equality would have passed too; the leading-path rule was not needed here |
| The authorization server's document at the third location, and the placeholder `issuer` | The server names `organizations/v2.0`. Its public document is at the appended location and its `issuer` holds `{tenantid}`, as on the common endpoint, and the output shows the issuer as the server named it |
| Scopes from the challenge, then the server's metadata | From the server's metadata. The scope is the server's URL followed by `/.default`, together with `openid profile offline_access` |
| `offline_access` added when the authorization server lists it | Not exercised: the server's list already holds it, so nothing was added and the output says only "from the server's metadata" |
| No `resource` parameter, no PKCE-advertisement check, no `issuer` check | The login completed with all three left out |
| The refresh request carries no `scope` | Accepted. The renewal returned a new refresh token, which replaced the stored one |

**Where the stand-in differed.** The stand-in of section 4 was built from
published documents. It names a tenant's own authorization server, serves its
metadata at a path of its own, and lists a single `api://` scope without
`offline_access`. None of that changes a decision.
`TestLoginAgainstWhatAgent365Publishes` adds the observed shape beside it.

**Other Agent 365 servers (reported 2026-11-18).** The same user reported that
the servers for SharePoint, Teams and OneDrive connected as well. Only the
result was reported: the servers' names, their responses and the logins'
output were not sent, and neither was whether the servers share one client
and one port.

**Still not observed.** What the Agent 365 servers other than `mcp_MailTools`
answer. The rule that adds `offline_access`, against Entra ID. What Entra ID answers when a `resource` parameter is sent
with `scope`. A server protected by Entra ID that is not Agent 365.
